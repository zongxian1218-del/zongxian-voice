# 媒体引擎 PL0 状态报告

日期：2026-10-04
范围：`src/media/`（Windows 音频采集 + 降噪 + 录音）
状态：**麦克风链路完全可用；立体声 + 降噪仍有缺陷**

> **【2026-10-06 追加：两条旧结论已作废，别照旧文档改代码】**
>
> 1. **`RingBuffer` 的单位是样本(float)，不是帧。**
>    旧文档（含 `docs\share-audio-status-2026-10-06.md`）说"帧/样本混淆已修"，
>    但当时 **API/注释写"帧"、两个调用点按"样本"用**。2026-10-06 已统一为
>    **样本**：`RingBuffer(capacity_samples)` / `Write(interleaved, samples)` /
>    `Read(out, cap_samples)` / `AvailableSamples()` / `DroppedSamples()`，
>    统计键名也从 `bufferedFrames` 改成 `bufferedSamples`。
>    谁照旧文档把调用点"改回帧"，立体声就会只写一半样本、左右交错错位。
>    契约写在 `src/media/src/audio/ring_buffer.h`，自检命令：`zxprobe ring-check`。
> 2. **采样率不是常量 48k。**
>    `ZX_SAMPLE_RATE` 只是请求值/默认值；实际生效值必须用 `zx_source_format()`
>    的 `sampleRate` 查（还有 `deviceSampleRate` / `resampled`）。
>    端点采集在设备不是 48k 时请求 WASAPI 的 AUTOCONVERTPCM 真重采样，
>    不支持就如实回退 —— 不再"静默按 48000 算"。自检命令：`zxprobe rate-check`。

### 4.3 进程回环（共享单个应用音频）—— 系统 API 直接崩溃

> **【2026-10-06 已作废 + 真因】本节（以及 §5 第 1 条、§6 末段、§7 全节）的
> 「崩溃来自系统 API 本身 / 必须做子进程隔离」结论已被推翻。原文全部保留在下面，仅作历史对照。**
>
> - **真因**：激活之后对指向**栈变量**的 `VT_BLOB` 调了 `PropVariantClear`
>   （→ `CoTaskMemFree(栈指针)` → 堆损坏 `0xC0000374`）。删掉那一行后探测 `rc=0 / supported=1`。
> - **代码现状（证据）**：`src\media\src\audio\wasapi_backend.cpp:859-877`
>   `ProbeProcessLoopback()` 自带注释「【2026-10-06 已修，默认走真实探测】」，
>   且 `ZX_ENABLE_PROCESS_LOOPBACK_PROBE` **已不控制任何代码分支**（全仓只剩注释提到它）。
>   所以下面「当前默认返回『不支持』、不做真实探测」不再成立。
> - **子进程隔离**：**不再是必须**（仍可作为纵深防御，但不是修这个 bug 的前提）。
> - 与此相反的另一处文档：`src\media\include\zongxian_media.h:166-169`
>   **【2026-10-06 已由引擎侧改掉】**（那段作废说明已替换为"默认真实探测 + 真因是
>   对栈变量 VT_BLOB 调 PropVariantClear"）。

```
dist\zxprobe.exe loopback-probe
```

直接调用 `ActivateAudioInterfaceAsync`（进程回环）会让进程以
**0xC0000374（堆损坏）** 终止。

已核实的事实：

- 完成回调的 IID 是正确的（SDK 里就是 `41D949AB-9862-444A-80F6-C261334DA5EB`，
  与官方示例一致）
- `PROPVARIANT` / `AUDIOCLIENT_ACTIVATION_PARAMS` 构造符合官方示例
- 崩溃发生在激活调用路径内，不是返回之后
- **SEH 拦不住**：堆损坏走 fast-fail，Windows 刻意让它绕过 `__except`

> **【已作废 2026-10-06，以下原文保留作历史】** 现在**默认执行真实探测**
> （`wasapi_backend.cpp:866-867`「所以现在默认执行真实探测」）；「为它崩溃整个程序不可接受」
> 这个理由也不成立 —— 崩溃是我们自己对指向栈变量的 `VT_BLOB` 调 `PropVariantClear` 造成的。

因此当前默认返回"不支持"并给出说明，不做真实探测。这是刻意的取舍：
探测只是为了决定界面上要不要显示"单个应用"这个选项，为它崩溃整个程序不可接受。

> **【已作废 2026-10-06，以下两条保留作历史】** 真正的修法是删掉那行 `PropVariantClear`
> （见本节顶部）。下面两条基于错误归因：子进程隔离仍可作纵深防御，但**不是修这个 bug 的前提**；
> 手写 COM 对象与真因无关。

正确修法（按推荐顺序）：

1. **子进程隔离**：起一个极小辅助进程去做激活，父进程只看退出码。
   子进程崩了就是"不支持"，主程序毫发无伤。这是与不可信系统 API 打交道的标准做法。
2. 手写最小 COM 对象替代 `WRL::RuntimeClass`，排除 `FtmBase`/marshal 机制是元凶。

## 5. 对后续"改用 WebRTC"的结论

这些经验与发现**不随技术路线改变**，换用 WebRTC 后依然适用：

1. **进程回环没有现成库能替代**。`miniaudio` 不支持，WebRTC 也不暴露。
   任何方案都得自己调 `ActivateAudioInterfaceAsync`，并且**必须做子进程隔离**——
   因为崩溃来自系统 API 本身，不是封装层的问题。
   **【2026-10-06 已作废】上面这条「必须做子进程隔离」是错的** —— 崩溃来自我们对指向栈变量的
   `VT_BLOB` 调 `PropVariantClear`，不是系统 API（真因与证据见 §4.3 顶部）。
2. **"单个应用音频"在整个方案里是最不确定的一块**，建议单独排期、单独验收。
3. **AEC 参考信号必须包含"你要播放的一切"**（对端语音 + 本地共享音频）。
   只把对端语音当参考，会导致"开共享音频后听到自己声音的两重回音"。
   这一条在 WebRTC 里同样成立。
4. **降噪效果必须有客观指标兜底**。本次就是靠"纯重建定标测试"（单位增益下
   重建增益必须 ≈ 1.0）才发现 -5.5 dB 的音量错误——这种错误不崩溃、不报错、
   日志全正常，只靠耳朵听很可能归因成"降噪算法就这样"。
   建议 WebRTC 路线也保留同类的定量验收。
5. **噪声底要用最小值统计，不能用普通指数平滑**。否则稳态信号会被学成噪声。
   这个结论对任何谱减类实现都成立。
6. 采集侧的两个通用陷阱（与库无关）：
   - 一次读取的缓冲必须按 **帧数 × 声道数** 分配，只按帧数开会静默越界
   - 循环结束条件必须用**真实墙钟**，不能用"循环次数 × 超时"，否则会出现
     "录 5 秒只得到 0.3 秒音频"却不报任何错

## 7. 进程回环（单应用音频）实测复验 —— 2026-10-05 【归因已作废，见 §4.3 顶部更正】

> **【2026-10-06 已作废（归因错误）】** 本节记的现象（`0xC0000374`、SEH 拦不住、父进程安然无恙、
> 崩溃在激活路径内）是真实观察，但把它**归因成「系统 API 直接崩溃」是错的**（真因见 §4.3 顶部），
> 因此下面「结论全部成立」「必须子进程隔离」作废。原文保留作历史。

§4.3 的"系统 API 直接崩溃、必须子进程隔离"这次用**打开真实探测 + 独立进程**复验了一次，
结论全部成立，并多抓到三条细节。

**怎么复现**（脚本已入库）：
`build\build-media-loopback-probe.cmd`（带 `-DZX_ENABLE_PROCESS_LOOPBACK_PROBE`，
建到独立目录，不动正常构建）→ 在**一次性进程**里跑 `zxprobe.exe loopback-probe`。
注意：路径要用环境变量传（仓库在非 ASCII 路径下，写进 .cmd 会被 OEM 代码页毁掉，
脚本里已记这个坑）。

**实测结果**：

| 观察 | 值 |
|---|---|
| 退出码 | `-1073740940` = **0xC0000374**（堆损坏） |
| 事件日志 | `Faulting application: zxprobe.exe` / `Faulting module: ntdll.dll` / `Exception code: 0xc0000374` |
| 崩在哪一步 | 打印 `[1/4] …` 之后、`[2/4]` 之前 → **激活调用路径内**（与 §4.3 一致） |
| SEH 包装 | **没能拦住** → 证实"SEH 拦不住堆损坏" |
| 父进程 | **安然无恙** → 证实"子进程隔离"是可行方案（第一次用真实崩溃验证，不再是推论） |

**顺手更正一处文档与代码不一致**：`include/zongxian_media.h` 早先写"这是**真实探测**
（调一次 ActivateAudioInterfaceAsync）"，但那段代码由 `ZX_ENABLE_PROCESS_LOOPBACK_PROBE`
控制且**默认未定义** —— 线上一直返回写死的"不支持"。注释已改正并记录本次实测。

**对做这个功能的含义（设计草图）**：捕获**必须留在子进程里** ——
音频客户端句柄不能跨进程转移，所以"子进程只探测、主进程去捕获"不成立。
可行形态：**一个专门的音频捕获子进程**（做激活 + 抓 PCM），PCM 经管道/本地 socket 交给主程序；
子进程崩了就当"本机不支持"，界面回落到"共享全部应用的声音"，主程序毫发无伤。

### 7.1 捕获子进程（父侧）实测 —— 2026-10-05

新增 `build\audio-capture-host.py`：**父进程侧**的决定逻辑，同时是验收工具。

```
python build\audio-capture-host.py --selftest
```

实测结果（`tmp\capture-host-selftest.txt`）：

| 路径 | 结果 | 说明 |
|---|---|---|
| ① `--kind process`（单个应用音频） | 子进程 **rc=2** 干净退出，父进程存活 | 引擎按设计拒绝："本机对应音频宿主暂未开放…需要先做子进程隔离。当前请使用『共享全部应用的声音』" → **降级决策成立** |
| ② `--kind loopback`（降级路径：共享全部应用的声音） | 子进程 **rc=2**，`无法开始录音` | **在本开发环境里起不来**。但引擎已成功读到实际格式 `48000/2ch/32bit float` → **不是设备缺失**，更像沙箱挡了音频流 |
| 崩溃隔离（`loopback-probe` + 打开真实探测） | 子进程 **0xC0000374**，父进程安然无恙 | §7 那一节已实测（同一台机器） |

**结论**：
1. **"把危险调用关进子进程"这条架构已成立**（干净降级 + 崩溃隔离两种形态都实测到了）；
2. 但**降级路径本身（整机 loopback 采集）在本环境跑不起来**，需要在**不受沙箱限制的机器**上复测；
3. 产品侧还差两步：父进程用 C#（现在只有 Python 验收工具）、真机验证两条路径。

配套的写入位置教训：让被拉起的 exe 写文件时，**输出路径要放在工程内**（本机禁止写工程外）；
不过本轮验证过，`--kind loopback` 的失败**不是**写入位置造成的 ——
写工程 tmp、写 exe 自己目录、把 exe 搬到 tmp 后再写，三种都一样失败。
