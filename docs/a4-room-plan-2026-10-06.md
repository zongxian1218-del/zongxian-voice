# A4「房间概念」方案（待你定方向）—— 2026-10-06

> 用户原话："没有建立房间功能，就是你要连自己的房间，得连自己的 IP，很别扭。"
> 这属于**产品形态**变更，按规矩先给方案、你拍板，我再动手。

## 1. 现状（都是实测过的仓库事实）

| 能力 | 现状 | 位置 |
|---|---|---|
| 信令 | **每台机器自己起**：房主开 `ws://0.0.0.0:端口/signal`，加入方必须知道房主 IP:端口 | `SignalingServer.cs` |
| 局域网发现 | **已实现**：UDP 45880 每秒广播名片，同网段自动出现在"房间列表"，点一下就加入 | `LanDiscovery.cs` |
| 房间名 | 有（`--room` / 设置里可填），但**只用于分组**，不解决"怎么找到对方" | `AppConfig.CallPageName` 附近 |
| 跨网段 | 设置里有 **TURN 中继**填字段（`turn:…`），空着就是 STUN-only | `MainWindow.xaml` 538+ |
| 加入入口 | 界面上有"联机/换房间"浮层：贴地址、或从局域网列表选 | `JoinButton` / `JoinRoomButton` |

**结论**：用户觉得别扭的根因不是"没有房间概念"，而是 **信令必须由某一方提供公网可达地址** ——
同网段已经被局域网广播解决了，跨网段就卡在"谁来当中继点"。

## 2. 四个可选方向（含取舍，必须你选）

### 方向 1：局域网**零运维**方案（今天就能做完，不加任何基础设施）
- 把现状做到"不别扭"：**邀请码 = 房间名 + 地址**合成一条可复制的串；界面上做成
  「**创建房间**」→ 弹出"把这串发给朋友" + 一键复制；对方「**加入房间**」→ 粘贴即进。
- 局域网里进一步：**按房间名列表显示**（现在显示的是"机器名｜房间"），并支持**搜索/双击进入**。
- 优点：0 部署、0 账号、今天就能出包；把"填 IP"降级成"复制一串/选一下"。
- 缺点：**跨网段仍然要房主端口可达**（或用户自己用组网工具/TURN）。

### 方向 2：**自建公网信令**（真正的"房间号"体验）
- 部署一个常驻信令服务（很小的 WebSocket 中继，仓库里 `SignalingServer` 稍加改造就能当服务端）；
- 客户端只填 **6 位房间号**（或房间名+密码）→ 连公网信令 → 自动互相发现；
- 媒体仍然 P2P（打不通时走 TURN）。
- 优点：体验最好，跨网段可用，不需要房主开端口。
- 缺点：**需要一台常驻服务器**（月租/域名/证书/运维），且要做**滥用与隐私**方面的取舍
  （信令能看到谁和谁在一个房间；内容仍是端到端加密的）。

### 方向 3：**第三方信令**（如公共 WebSocket 中继/Pastebin 式交换）
- 优点：不自己运维。
- 缺点：依赖别人的可用性与策略；隐私与稳定性不可控；可能随时失效。**我不推荐**。

### 方向 4：**打洞优先 + 公网会合点**（高级）
- 需要一个极小的"会合点"只交换候选地址，然后 UDP/TCP 打洞；
- 优点：省中继带宽；缺点：**打洞成功率不是 100%**（对称 NAT 必失败），
  仍然要 TURN 兜底，且实现复杂度高（仓库已有 `PunchHoleStatus/`，但那是**你私有的另一个项目**，我不会动）。

## 3. 我的建议（分两步，风险与收益都清楚）

**第一步（立刻做，方向 1）**：把"填 IP"变成"**创建房间 → 复制邀请串 → 粘贴加入**"，
并把局域网列表做得好用（按房间分组、可搜索、双击进入）。
- 判据：双实例 + 三实例下，"创建→复制→粘贴→加入"全流程可自动跑通，且不需要手抄 IP。
- 这一步**不改变"谁提供信令"**的本质，但把用户感知从"填 IP"降到"贴一串"。

**第二步（等你决定要不要服务器）**：如果将来有常驻服务器，方向 2 的"6 位房间号"可以
直接接在第一步的邀请串之上（邀请串里带的就是 `信令地址 + 房间名`，换成服务器地址即可）。

**为什么建议先第一步**：它今天就能出包、不需要你投入任何基础设施，而且**第二步不会被它挡路**。
反过来先做方向 2 的话，我必须先知道：服务器放哪、谁付、要不要账号体系 —— 这些是你的决定。

## 6. 已实施（本轮，全部实测过）

### 6.1 局域网列表：从"分不清"到"能选对"
**实测问题**（三实例同房间）：
```
[局域网] 发现 2 个房间：PC-20260617QEOO｜房间 周末开黑｜26.103.67.21:46672；
                        PC-20260617QEOO｜房间 周末开黑｜127.0.0.1:46671
```
同一台开发机上机器名相同、房间名相同，**只有端口不同** ⇒ 用户没法一眼选出该连哪个。

**改法**：
- 标签改成 `房间 周末开黑 · PC-20260617QEOO · 端口 46671`（房间名在前、端口单独标出）；
- `LanRoom` 增加 `SearchText`（房间/机器/IP/端口的合并文本），供筛选用；
- 房间列表变成**可输入**：输入关键字即筛选（不写死任何名字），
  **筛选后只剩一个候选时自动选中** ⇒ 一次回车就能加入；
- 回车提交不等同于静默：没匹配到 / 一个房间都没有，都会在应用日志里说清。

### 6.2 邀请串：把"房间名"一起带走（消除跨网段手抄的别扭）
**实测问题**：原来的"复制地址"只复制 `ip:端口`，**不带房间名** ⇒ 对方连上后还得手动把
房间名改成一致，否则两人不在同一房间。

**改法**：
- 复制按钮改为复制 **邀请串** `房间名@地址`；
- 加入时**同时认三种写法**：邀请串 / `zongxian://room/房间名@地址` / 旧写法（只给地址）；
- 粘贴邀请串时**自动把房间名填进输入框**并写一行日志说明。

**离线单测（新增第 24 项闸门）**：`--parse-invite-test` 跑 6 条用例，
**当场抓到一个真 bug**：房间名自身带 `@` 时应该取**最后**一个 `@` 作为分隔符，
原实现用第一个 ⇒ `name@host:1234@1.2.3.4:5678` 会把地址解析错（连到错误地址）。
修好后 6/6 PASS，并固化成 `check_invite_parse()`（离线跑，任何环境都能验证）。

### 6.3 明确**没做**的事（等你后续决定）
- 没有"创建房间"独立入口（房间名仍在设置里改）；
- 没有公网信令 / 6 位房间号（需要你决定服务器归属）；
- 没有注册 `zongxian://` 系统协议（可点击形态只是**能被解析**，系统级唤起要改注册表/安装项）。
