# 第一部分 · 目标架构

## 1. 分层（三层 + 一条唯一通道）

```
┌─ 前端：页面（WebView2 里，只管展示与交互） ─────────────────────────┐
│  壳 shell（窗口/面板/路由/主题）── 不含任何业务                     │
│  模块 UI：voice / chat / file / shareaudio / screen                 │
│    每个模块只做两件事：订阅"自己模块的事件"改自己那块 DOM；          │
│                        用户操作 → 发"命令"（不直接碰 WebRTC/信令）   │
└───────────────────────▲──────────────────────────┬─────────────────┘
              事件（页面→C#）                  命令（C#→页面）
        {module, type, payload}          {module, action, payload}
┌───────────────────────┴──────────────────────────▼─────────────────┐
│  桥 bridge：**唯一通道**，两侧都用注册表声明自己的消息，启动时对账    │
└───────────────────────▲──────────────────────────┬─────────────────┘
┌───────────────────────┴──────────────────────────▼─────────────────┐
│  后端：C# 模块宿主 + 插件端口                                        │
│    IModule / IModuleHost（见 §3）                                    │
│    模块：VoiceModule ChatModule FileModule ShareAudioModule          │
│          ScreenModule                                                │
│    基础设施（模块共用，不允许模块自己造）：                           │
│      MediaBridge(WebView2) · Signaling · EngineProbe(zxprobe 封装)   │
│      LanDiscovery · Storage · Logging · Config                       │
└───────────────────────▲──────────────────────────┬─────────────────┘
              采集/播放（流式 PCM / 设备与会话枚举）
┌───────────────────────┴──────────────────────────▼─────────────────┐
│  引擎（C++）：只提供三种原语 —— 设备/会话枚举、采集流、播放         │
│    接口契约写进 zongxian_media.h（单位、线程、生命周期，见 §6）       │
└────────────────────────────────────────────────────────────────────┘
```

**铁律**：命令与事件**只能**走桥；模块之间**不许直接调用**（要协作就通过宿主转发事件）。

## 2. 五个模块的边界（各自独立状态与生命周期）

| 模块 | 只负责 | 不负责（过去混在一起的） |
|---|---|---|
| **voice 语音** | 麦克风采集、编解码档位、静音、电平表、通话状态显示 | 不碰聊天/文件/屏幕；不直接操作链路 |
| **chat 文字** | 消息收发、气泡渲染、日期分隔、发送者名字、未读提示 | 不碰文件传输（文件走 file 模块，只借用聊天通道传元数据） |
| **file 文件** | 分片、校验、断点、落盘策略、路径安全、进度 | 不碰 UI 文案；落盘路径由 Storage 提供 |
| **shareaudio 共享电脑声音** | 采集进程生命周期、50ms 分块、独立音轨、来源枚举、独立开关与状态 | **不依赖屏幕共享**（这是用户明确要求） |
| **screen 屏幕共享** | 采集源选择、视频轨发布、观看端渲染、失败原因 | 不碰共享音频（音频走 shareaudio） |

> 屏幕共享的"选择窗口"是 Chromium 的设计（`ScreenCaptureStarting` 只能允许/取消，**不能代选源**），
> 该结论写进该模块文档，避免后人再试。

## 3. 插件端口（预留，新功能不改宿主）

```csharp
public interface IModule
{
    string Id { get; }                       // "voice" / "chat" / "file" / "shareaudio" / "screen"
    string DisplayName { get; }
    Task StartAsync(IModuleHost host, CancellationToken ct);
    Task StopAsync();
}

public interface IModuleHost
{
    IMediaBridge   Media   { get; }   // 唯一能调页面的入口（强类型，见 §4）
    IEngineProbe   Engine  { get; }   // zxprobe 封装：枚举设备/会话、开采集流
    ISignalBus     Signals { get; }   // 房间/链路事件（谁加入、谁离开、链路状态）
    IStorage       Storage { get; }   // 落盘、路径安全、命名规则
    IConfig        Config  { get; }   // 端口、超时、采样率等唯一来源
    ILogger        Log     { get; }
}
```

- **注册**：`ModuleRegistry.Register(new VoiceModule())` —— 宿主只认接口，不认具体类
- **加模块的代价**：新增 1 个 `IModule` 实现 + 1 个前端 UI 模块 + 在两侧注册表各加一行；
  **不允许**改 `MainWindow`（它只做绑定与展示）
- **端口即规范**：模块拿不到的东西（例如直接 `Process.Start`、直接 `ExecuteScriptAsync`）
  就是它**不该做的事**

## 4. 契约：消息注册表 + 启动对账（消灭"双向对不上"）

```csharp
// 两侧各声明自己能处理什么；启动时对账，对不上直接报错（不是打日志）
static readonly TypeRegistry Bridge = new()
{
    // 页面 → C#：每个 type 必须有人处理
    Events = { "devices", "roster", "chat-message", "file-progress", "call-link",
               "screen-source", "share-audio-debug", "incoming-call", /* … */ },
    // C# → 页面：每个方法名必须存在
    Commands = { "join", "call", "sendChat", "sendFile", "startScreenShare",
                 "startSharedAudio", "pushSharedAudio", "shareAudioDebug", /* … */ },
};
```
- **启动握手**：页面加载后 C# 调 `engine.methods()` 取页面真实方法名集合 → 与 Commands 求差集 →
  缺一个就**拒绝对外可用**并写明确日志（现在 `listMethods()` 存在但没人调）
- **回归守卫**：`run-checks.py` 增加一项 —— 扫描两侧注册表，出现"页面发但无 handler"或
  "C# 调但页面无此方法"就 FAIL（今天就是靠肉眼才发现 `devices` 没人处理）

## 5. 前端模块化（页面不再是一个 2800 行文件）

```
media/
  shell.html            壳：布局/主题/面板容器；不含业务
  core/
    bus.js              命令/事件收发（唯一 postMessage 出口）
    store.js            单一状态源（按模块切片，禁止模块级散落变量）
    link.js             链路对象：一条 PC 的全部上下文（**替代隐式单例**）
    log.js              日志：规则是"任何失败必须上报"，纯 DOM 日志只给界面文本
  modules/
    voice.js  chat.js  file.js  shareaudio.js  screen.js
```

**必须做对的一件事（病根 1 的解药）**：把 `link` 变成**显式参数** ——
凡"按链路做的事"（音频上报、统计、屏幕轨、共享声音、聊天）都必须接收 `link`，
不再有 `state.pc` / `state.remoteId` / `chatChannel` / `screenSender` 这些单例别名。
这一步做完，`ontrack` 互相覆盖、停止共享后静音、第二人看不到画面会**一起消失**（同一根因）。

## 6. 引擎契约（单位、线程、生命周期写进头文件）

- **单位**：`RingBuffer` 的 API、注释、统计键名统一为**样本(float)**；调用点传样本数
  （现状是 API 说帧、调用点给样本 —— 谁照文档改谁引爆）
- **采样率**：把"48 kHz"从注释级契约升级为**运行时不变量**：不是 48k 就明确报错或真正重采样
  （现状：44.1k 设备静默变调）
- **线程/生命周期**：`stats` 改原子快照；`zx_source_close` 与 `zx_source_read` 互斥（现状有释放后使用）；
  头文件写明"Start/Stop/Close 不得与 Read 并发"
- **文件拆分**：`wasapi_backend.cpp`（1139 行 / 7 职责）→
  `device_enum` / `session_enum` / `probe` / `wasapi_source` / `sample_convert`
- **清理**：删假开关（`master_volume`/RNNOISE/`logLevel`/内存哨兵/`sanitized_`/无用回调 API），
  或把它们真正接上

## 7. 迁移计划（每阶段都能独立验证，不搞大爆炸）

| 阶段 | 做什么 | 完成判据（客观） |
|---|---|---|
| **S0 止血** | 修审计里的 11 个真 bug（§三）+ 删我们自己的脚手架/死代码 + 改掉与代码相反的文档 | `smoke-ui` + `run-checks` 全绿；错误提示能被看见（人工确认 2 条） |
| **S1 立契约** | 消息注册表 + 启动对账 + 回归守卫扫双向差异 + `IConfig` 收敛端口/超时/采样率 | 守卫能故意报出一次"人为制造的 type 不匹配" |
| **S2 拆桥** | 从 `MainWindow` 抽出 `EngineProbe` / `SharedAudioService` / `NetworkProbe` / `FileStore` / `ScreenShareService` | `MainWindow` 降到"绑定与展示"（无 `Process.Start`、无 `JsonDocument.Parse`） |
| **S3 拆页面** | `call.html` → shell + core + 5 个模块；**link 显式化**，删单例别名 | 双实例/三实例自检通过；共享声音的"停一次再开"仍能出声（回归病根 2） |
| **S4 装端口** | `IModule`/`IModuleHost` + 5 个模块注册 | 新加一个"空模块"只需 2 个文件、0 处改 `MainWindow` |
| **S5 拆引擎** | 按 §6 拆文件 + 单位/线程契约 + 删假开关 | 引擎自测（`nstest`/探针）通过；44.1k 设备行为明确（报错或重采样） |
| **S6 文档固化** | 本文件 + 审计总结 + 清理已过期文档（STATUS/handoff/fix-plan 互相矛盾处） | 文档里不再有"与代码相反"的结论（抽查 5 处） |

**顺序理由**：S0/S1 不动结构却能立刻减少"改一处坏一处"；S2/S3 是收益最大的两步；
S5 可以并行（引擎与 UI 边界清楚）。

# 第二部分 · 后续开发规范（以后每个功能都照这个做）

## A. 加一个功能的标准动作

1. **先定模块归属**：它属于 voice / chat / file / shareaudio / screen 哪个？
   都不属于 → 说明要新开一个模块（照 §3 的端口实现，不改宿主）
2. **先写契约**：在两侧注册表里加消息 type / 命令名，**再**写实现
3. **后端**：新建 `XxxModule : IModule`，依赖只从 `IModuleHost` 取；不许 `Process.Start`、
   不许直接 `ExecuteScriptAsync`、不许解析引擎 stdout（那是 `IEngineProbe` 的事）
4. **前端**：新建 `modules/xxx.js`，只改自己那块 DOM；状态放 `store` 的自己的切片；
   **任何失败必须上报**（不许只用 `log()` 写隐藏 DOM）
5. **状态**：一个事实只存一处。需要"跨链路"就遍历 `links`，不许再造单例别名
6. **测试**：`build\smoke-ui.py` 加一条**真实用户动作**的断言（模拟键鼠 + 轮询等待 + 看门狗），
   不许用固定 sleep、不许"控件存在就算通过"
7. **文档**：模块一句话说明 + 已知边界（例如"屏幕共享的选择窗口由用户决定"）

## B. 禁止清单（今天踩过的都在里面）

- ❌ 写死：开发机绝对路径、端口、版本号、采样率、超时、阈值、颜色 —— 一律进 `IConfig`/主题
- ❌ 双入口：同一个功能既有环境变量入口又有界面入口（今天的 `ZX_SHARE_AUDIO`）
- ❌ 假开关：配置项/接口声明了却不生效（引擎里有 7 个）
- ❌ 只在注释里写约定（单位、线程、生命周期）—— 必须落到类型/断言/头文件契约
- ❌ 让文档晚于代码：结论被推翻就**当场**改文档，或标"已作废"
- ❌ 构建链靠人记：任何"记得拷文件/刷清单"的步骤都要变成脚本或回归守卫
- ❌ 静默失败：`>nul 2>nul` 吞错、异常被空 catch 吞掉（今天"后台线程调 WebView2 失败"就是这样被藏了两轮）

## C. 交付前必须过（机器判，不靠人）

1. `build\run-checks.py` 全绿（含：界面自检用模拟键鼠、dist 卫生、
   **版本一致性**、**契约双向对账**、传输层自测）
2. `build\make-voice-package.py --version NN` 回读自检 `[OK]`（关键文件不缺、无排除类型混入）
3. `BUILD-INFO` 的 `commit` == 当前 HEAD（否则溯源守卫会拦）
4. 每一条"修好了"都附**可复核证据**：数字（字节/能量/坐标）或日志片段，不接受"应该好了"

## D. 验收方式（用户侧）

`docs\测试清单-共享电脑声音.md` 是样例：只用鼠标、3 分钟、每步写清"期望什么"，
出问题用"复制诊断信息"回传。以后每个模块都配一份同样形态的清单。
