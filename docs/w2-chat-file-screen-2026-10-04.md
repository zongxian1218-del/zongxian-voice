## 1. 文字聊天

### 1.1 为什么走 DataChannel 而不是信令服务器

信令服务器是自己控制的，本来可以直接中继聊天。但 DataChannel 更合适：

- **端到端加密**（DTLS），服务器看不到聊天内容 —— 朋友之间的对话本该如此
- 不增加服务器负担，也不在别人机器上留聊天记录
- 与语音**互相独立**：可以只聊天不打电话，也可以边聊边打

代价：必须先与对端建立连接才能聊天。对"已经连上的人之间聊天"完全够。

### 1.2 与通话解耦

原实现里「建立连接」和「开始通话」是同一件事（进房间就自动拨号）。
改成：

- **进房间 → 自动建立链路**（只为聊天，不动麦克风）
- **点「发起通话」→ 才开麦并重协商加音轨**

改动理由：自动打电话会突然占用对方麦克风，很打扰。聊天链路是无感的。

### 1.3 实测证据

```
A（接收方）:                         B（发送方）:
  连接状态: connected                  连接状态: connected
  聊天通道已打开（端到端加密）          聊天通道已打开
  [收到消息] 你好这是DataChannel消息    【聊天测试】已发送
```

## 2. 文件传输

### 2.1 为什么没有复用 transfer.py

仓库里已有 1318 行的多流 TCP 传输引擎（`src/swiftdrop/transfer.py`），
能力更强：多流并行、断点续传、4MB SHA-256 分块校验。

**没有复用的理由**：

| 维度 | transfer.py | DataChannel |
|---|---|---|
| 依赖 | 需要 Python 进程 | 无（页面内建） |
| 端口 | 需另行协商 | 无 |
| 加密 | 需自己加 | DTLS 端到端 |
| 分片/保序/流控 | 自己实现 | 协议自带 |
| 超大文件（>1 GB） | **更强** | 受内存限制 |

对"两个人之间传文件"，简单可靠比多流并行重要。
**超大文件应该回到 transfer.py 那条路** —— 这是后续可选项，不是当前必需。

### 2.2 实现要点

**分片 16 KB**：太小则消息头开销占比高，太大则一帧占内存过多、
`bufferedAmount` 判断会抖动。

**必须做背压**：DataChannel 的发送缓冲**没有上限保护**，无脑 `send`
会把内存吃爆。所以每片前检查 `bufferedAmount`，超过 4 MB 就等：

```js
while (chatChannel.bufferedAmount > HIGH_WATER) {
  await new Promise(r => setTimeout(r, 20));
}
```

**文本与二进制分离**：分片走二进制帧（前 4 字节存序号），控制消息走
JSON 文本。这样高频大流量不经过 JSON 解析。

### 2.3 踩坑：落盘目录不能写死

第一版写死 `%USERPROFILE%\Downloads\棕仙语音`，实测直接抛：

```
UnauthorizedAccessException: Access to the path
'C:\Users\Administrator\Downloads\棕仙语音' is denied.
```

**非提权进程常常不能写"下载"目录**，哪怕路径看起来属于自己的用户目录。

改成**按可写性探测**，依次尝试并返回第一个真正能写的：

1. 用户「下载」目录（最符合预期）
2. `exe\received\`（便携，几乎总能写）
3. 临时目录（兜底，至少不丢文件）

探测时必须**实际写一个文件**，不能只 `CreateDirectory` ——
有些目录能建子目录但写不了文件。

同时把最终保存路径写进日志：用户找不到文件是最糟的体验。

## 3. 屏幕共享

### 3.1 画面显示的关键决策

**视频帧不跨进程传递。** 帧在 Chromium 进程内部，逐帧搬到 C# 再画
代价极高（每帧几百 KB × 30fps）。所以让 **WebView2 就地渲染**：

- 平时：`MediaHost` 是 0×0 的隐藏媒体宿主
- 共享时：C# 把它放大成一块显示区（`ScreenView`），画面由 Chromium 自己渲染

几乎是零成本，且不需要任何帧格式转换。

### 3.2 参数选择

| 参数 | 取值 | 理由 |
|---|---|---|
| 帧率 | 15 fps | 屏幕共享很容易吃满带宽把语音挤坏 |
| 分辨率上限 | 1920×1080 | 防止 4K 拖垮带宽 |
| 视频码率 | 1.2 Mbps | 1080p15 的桌面内容够用，又不挤语音 |
| 音频 | `echoCancellation:false` | 共享的是内容音频，不该被当语音处理 |

### 3.3 音频范围（如实说明）

- **整个系统的声音**：Windows 上 `getDisplayMedia` 支持，已实现
- **单个应用的声音**：Windows 上浏览器**拿不到**，必须走 WASAPI 进程
  回环（`zxaudio_helper.exe`）。这是 W4 的内容。

### 3.4 用合成画面验证传输链路（关键方法）

屏幕共享的难点在于 `getDisplayMedia` **必须由用户在系统弹窗里选窗口**，
无法脚本化。如果因此就不验证，那么重协商、视频编码、对端收帧、
画面渲染全都没测过 —— 而这些恰恰是最容易出错的部分。

**做法**：用 `canvas.captureStream()` 造一路动态合成画面（会动的图形 +
帧号 + 时间戳），替代 `getDisplayMedia`。除了"采集源"不同，
后面的每一步都是**完全同一条代码**。

这把可自动验证的边界推到了最大，把人工验证缩小到只剩"选窗口"这一个
系统交互。

**实测结果**（`--screen-test`，A 接收方日志）：

```
18:42:43  收到画面帧 1 帧    (320×180)
18:42:45  收到画面帧 29 帧   (320×180)     ≈15 帧/秒
18:42:49  收到画面帧 90 帧   (480×270)     ← 分辨率随带宽自适应爬升
18:42:56  收到画面帧 180 帧  (640×360)
18:43:06  收到画面帧 331 帧  (960×540)
18:47:14  收到画面帧 3777 帧 (1280×720)    ← 持续 4.5 分钟无中断
```

**这份数据能证明什么**：

| 观察 | 结论 |
|---|---|
| 帧率稳定 15 fps | 与设定值一致，编码没有卡顿 |
| 分辨率 320×180 → 1280×720 自适应 | WebRTC 带宽估计正常工作 |
| 3777 帧持续 4.5 分钟无中断 | 无内存泄漏、无累积性故障 |
| `framesDecoded` 持续增长 | 视频轨真的在传输并解码，不只是协商成功 |

`framesDecoded` 持续增长这一点最重要：**只有 track 到达是不够的** ——
编码失败或协商不对时 track 也会到，但一帧都解不出来。

### 3.5 还差什么

- **真实屏幕采集**：需要用户点一次系统弹窗选窗口。
  已实现并自动验证的是：权限流程、错误路径（含用户取消）、
  合成源的完整传输链路、状态切换、重协商（开始与停止两向）。
- **AEC 参考信号**：见 §3.4，仍是已知风险。

## 4. 工程改进：把验证做成脚本化

这轮最大的方法改进：**不再靠截图验证**。

加了两个命令行开关：

| 开关 | 作用 |
|---|---|
| `--log-file <路径>` | 引擎日志实时落盘 |
| `--chat-test <文本>` | 连上后自动发一条消息 |
| `--file-test <路径>` | 连上后自动发该文件 |
| `--record-test` | 录 3 秒麦克风并落盘 |
| `--signal-test` | 合成正弦波跑编解码往返 |

代价对比：一张全屏截图进上下文约几万 token，而 `grep` 日志几乎为零。
**这是本次会话在 token 消耗上学到的最重要一课。**

### 4.1 也加了全局 JS 错误捕获

本会话踩过两次"JS 异常被静默吞掉"：

1. `setInterval` 回调抛异常 → 统计莫名其妙停止更新，日志毫无线索
2. SDP 改写函数抛异常 → 通话直接建不起来，界面只是"没反应"

现在 `window.onerror` 与 `unhandledrejection` 都上报到 C#，
任何未捕获异常都会出现在日志里。
