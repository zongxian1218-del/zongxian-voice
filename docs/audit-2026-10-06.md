## 二、四个"同一个病根"（这是重点）

审计三块各自独立得出，但指向同一件事：

### 病根 1：隐式单例 vs mesh 多链路（页面层）
页面按"只有一个对端"写：单 `state.pc`、单 `remoteAudioEl`、单 `chatChannel`、单 `screenSender`；
可产品要 mesh（3 人）。于是：
- `ontrack` 只有两路分支（video / 其余 audio），**后到的音频会覆盖先到的**（`call.html:1247-1301`、`1613-1622`）
- 同样的事实存两份（`links` Map 与 `state.pc`/`state.remoteId` 别名，6 处写、读几乎都走别名）
  → **3 人通话时第二个对端的音频状态永不上报**（`reportCallState` 只查 `state.pc`，`call.html:782-819`）
- 共享电脑声音那条**常驻音轨**与通话语音**共用同一个播放元素**，互相覆盖

### 病根 2：一个类/文件承担全部职责（三层都是）
- `MainWindow`：既是窗口又是业务层 —— 协议解包、进程/网络/文件 IO、**600 行验收脚手架**全在里面
- `call.html`：状态 + 信令 + mesh + 屏幕共享 + 共享声音 + 文件传输 + UI 全在一个文件
- `wasapi_backend.cpp`：7 类职责，导致同一件事（设备获取、meter、格式、初始化序列）**各有两三份实现**
- 后果：单位（帧/样本）、线程、生命周期这些**假设只活在注释里**，所以才会反复出现同类 bug

### 病根 3：C# ↔ JS 的契约是裸字符串（双向都对不上）
- C# 调用 **22 个方法名**：名字层面对得上 ✓（但**无类型、无返回值检查**）
- 消息 type **57 种**，双向都有对不上：
  - 页面发、C# **无 handler**：`devices` / `ice-state` / `remote-stats` / `chat-state` / `engine-methods`
  - C# 有 handler、页面**从不发**：`link-replaced` / `link-busy` / `share-audio-attach-skipped` / `stats-debug`
- 唯一本可兜底的 `listMethods()`（方法名对账）**自己没人调用**

### 病根 4：文档与代码相反（会误导下一个人）
- `src\media\STATUS.md:118-144` 至今写着"进程回环是系统 API 的锅、0xC0000374、必须子进程隔离"
  —— 2026-10-06 已用最小复现推翻（真凶是对指向栈变量的 `VT_BLOB` 调 `PropVariantClear`）
- `zongxian_media.h:166-169` 仍说"线上一直返回写死的'不支持'"，而代码早已无条件真实探测
- `noise_suppress.h:48-49` 仍写"声道 1 或 2"，生产路径其实恒为 1
- `docs\share-audio-status-2026-10-06.md` 记的"帧/样本混淆已修"与现状不符：**调用点按样本、API 按帧**，
  谁照文档去"修正"调用点就会二次引爆

## 七、构建与交付层审计（第四块，2026-10-06 追加）

这一块把前面三块的问题"放大"了：**功能层有 bug 是一回事，交付流水线没有强制力是另一回事。**

### 7.1 最硬的三条事实（可复现）

1. **已生成的 `dist\棕仙语音-测试版-v36.zip` 不可信**
   - 包内 `media/call.html` = **118,760 B**（sha256 `1ad677d4…`），源码 = **119,398 B**（`BD9EC195…`）
   - 拷贝 mtime 05:01:13 → 打包 05:04:21 → 源码改动 05:08:42：**先打包、后改代码**
   - 这正是 `check_dist_media_and_probe()` 设来要挡的那一类，**闸门当时是 FAIL，包却出去了**
2. **同一个包里含测试残留** `received/zx-filetest.bin`（184,320 B）
   - 打包脚本 `EXCLUDE_DIRS` 只认 `.webview2/recordings/obj/bin`；守卫只按后缀黑名单
   - **两份清单都不认识 `received/`** —— v22 那 37 个日志的同类问题，**换个目录名复发**
3. **溯源文件是手写的**：`dist\winui\BUILD-INFO.txt` 的 6 行与 `tmp\fix-finalize.py` 逐字一致；
   而 `build-winui-cs.cmd` 自己只写 4 行（不含 `sources:`/`note:`）
   - 直接后果：改一行 `commit` 就能让守卫认为"产物=HEAD"；`sources: src/winui-cs` 还把 `src/media` 排除在外

### 7.2 机制层的病根（比单个 bug 重要）

> **"自检"目前是一套并列的、可跳过的、事后可改写的旁路，而不是流水线里的一道闸门。**

- 守卫与打包是**两个互不调用**的脚本 —— 守卫 FAIL 不影响出包
- `run-checks.py` 里 **SKIP 不计入失败**（找不到 exe/探针就跳过最关键的两项，仍打印"PASS n / FAIL 0"）
- 参数写错（`run-checks.py dist`）→ **一项都不跑**，打印 `汇总: PASS 0 / FAIL 0`，看起来像通过
- `git` 不在 PATH 时，**溯源检查静默跳过**
- `build-winui-cs.cmd` 在 xcopy/pri 失败时**仍打印 `=== Build OK ===` 且退出码 0**
- "什么算残留"在**四处**各有一份定义（cmd / run-checks / 打包脚本 / dist-policy 文档），互不相同

### 7.3 其它高价值发现（摘要）

| 类别 | 事实 |
|---|---|
| 测试盲区 | `build\smoke-ui.py` **没有 `import re`**，而新增断言用了 `re.search` → 必然抛异常被兜成 FAIL；`run-checks` 又以 `[PASS] smoke-ui` 判定 → **"模拟键鼠"这条自检根本不可能通过，规矩四形同虚设** |
| 测试盲区 | 自检只跑**构建树**里的 exe；用户真实动作（解压 zip → 双击 `dist\winui` 那份）**从未被自动验证**，而历史故障（缺 pri / 缺 runtimeconfig / 旧探针）恰好只在交付物形态暴露 |
| 测试盲区 | `smoke-ui.py` 仍有固定 `sleep(1)`；C4 用**源文件文本**找 `RecordButton` 冒充"可用" |
| 交付约定 | `push-github.py` 的白名单**不含** `run-checks.py` / `smoke-ui.py` / `make-voice-package.py` / 两个主构建脚本 → 走那条路发布的仓库**没有守卫** |
| 重复冲突 | C++/WinRT 旧脚本 `build-winui.cmd` 与 C# 主线写**同一个** `dist\winui`；跑一次旧脚本就混入旧产物，守卫与打包都拦不住 |
| 重复冲突 | 同一个 `run-checks.py` 在四份文档里被说成 4/5/6 项（实际 7 项），版本号停在 v22/v24（实际 v36） |
| 文档矛盾 | `dist\RELEASES.md:21` 说"启动只显示欢迎窗口"，`docs\测试清单-共享电脑声音.md:14` 说"直接进主界面" —— **对同一个包说法相反** |
| 构建脆弱 | `build-media.cmd` 把 `zongxian_media.dll` 丢进 **dist 根**且 RELEASES 从未登记 → 每次构建媒体都让 dist 守卫 FAIL，只能人工挪隔离区 |

### 7.4 因此：`v36` 作废

- 该 zip 已从 `dist\` 挪进 `build\dist-quarantine-2026-10-06\`（按策略：挪，不删）
- **在"发版单一入口 + 闸门"做好之前，不再产出任何包** —— 否则每次都是在给用户发一个自己都不确定的产物

### 7.5 只允许做一件事的话

**把发版收敛成一个入口**（`build\release.py` 或 `.cmd`）：

```
构建 → 跑守卫（SKIP 一律按 FAIL）→ 生成 zip
     → 回读校验：zip 内 call.html/BUILD-INFO 与 dist\winui **逐字节一致**
     → 写 BUILD-INFO（含 sources: src/winui-cs, src/media）与 zip 的 sha256 进 RELEASES.md
除此之外：不允许手工打包、不允许手工改清单。
```

这正好也是本文 §五（我们自己新添的债）第 5 条的根治办法。
