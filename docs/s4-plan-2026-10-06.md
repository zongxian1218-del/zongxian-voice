## 3. 分歧点（必须你定，属"重大方向变更"）

1. **`IModule`/`IModuleHost` 是哪一侧的接口？**
   - (a) **C# 侧**：网页模块与原生模块用同一套宿主接口；
   - (b) **页面侧**：纯 JS 约定（每个模块暴露 `name / init(host) / dispose()`）。
   - 注：S2 拆的是 C#，S3 拆的是页面 JS。原文档没写死，两种都说得通。

2. **"装端口"要解决什么真实问题？** 现在 13 个模块都是**显式工厂 + io 注入**：
   `createMesh(io)` / `createSignaling(io)` … 已经是"端口"的实质。
   如果只是把 `io` 换成 `IModuleHost` 名字，收益是**形式统一**；
   如果要的是**生命周期**（统一 init/dispose、防止泄漏），那是**新能力**。

## 4. 两个可选方案

### 方案 A：轻量统一（推荐，1 个工作单元）
- 页面侧定义 `IModule` 形状：`{ name, init(host), dispose() }`；
- 13 个模块的工厂统一由 `module-host.js` 注册与编排（**初始化顺序**从"文件末尾一堆调用"变成声明式）；
- 加一道守卫：**每个模块必须能被 host 正常 init + dispose（含资源回收）**；
- 不新增功能，只把"接线"和"生命周期"收口，降低以后加模块的出错率。
- **风险低**：不改任何业务逻辑，双实例闸门 + 20 项守卫可回归。

### 方案 B：严格按原清单（2–3 个工作单元）
- 先补抽 `chat.js` / `shareaudio.js`（把 `call.js` 再降到 ~900 行）；
- 再给"5 个业务模块"装 `IModuleHost` 端口；
- 好处：与交接文档完全对齐；代价：`shareaudio` 与 `mesh` 耦合较深（建链时要挂轨），拆分需要重新划边界。

## 5. 我的建议

**选方案 A**，理由：
- S3 已经证明"工厂 + io 注入"这套能跑（20 项闸门 + 双实例 + 界面自检全绿），缺的只是**统一形状与生命周期**；
- `chat`/`shareaudio` 的独立拆分**收益低**（功能小、且 `shareaudio` 与建链强耦合），按方案 B 拆反而是为了对齐文档而制造风险；
- 真正卡着用户的不是模块形状，而是 **A 系列功能缺陷**（共享音频失效、成员列表只显示两人）。
