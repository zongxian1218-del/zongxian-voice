# 远程控制：鼠标注入 + 帧号绑定防陈旧点击（2026-10-05）

## 这一版做了什么

- **查看端**（`receiver-probe` 的覆盖窗口）：捕获鼠标移动 / 左右中键 / 滚轮 → 归一化成
  与分辨率无关的坐标 → 经**已有的**"接收端 → 发送端"控制通道（复用 `reqSock`，和关键帧请求同一条路）
  发出 `kTypeInput` 包。
- **被控端**（`sender-probe`）：收到后做**帧号新鲜度校验**，通过才用 `SendInput` 注入。
- **默认关闭**：两侧都必须显式加 `--remote-control`。正式应用要按设计文档 §9.5 走用户授权流程
  （默认焦点在"拒绝"、30 秒无响应即拒绝、被控时顶部常驻红条、全局快捷键停止控制）。
- **键盘这一版没做**（设计文档里键盘默认关闭，还要配合焦点处理）—— 载荷里 `vk` 字段已留好。

## 协议

用包头已有的 `type` 字段新增一种包：`kTypeInput = 3`，载荷是 12 字节的 `InputEvent`：

| 字段 | 含义 |
|---|---|
| `kind` | 0=鼠标移动 1=鼠标按键 2=滚轮 3=键盘（预留） |
| `flags` | 左/右/中键位 + `kInputDown`（按下） |
| `nx, ny` | 归一化坐标 0..32767 —— **与被控端分辨率无关** |
| `wheel` | 滚轮增量（WHEEL_DELTA 的倍数） |
| `vk` | 虚拟键码（键盘用，暂未实现） |

**帧号绑定（防"陈旧点击"）**：包头的 `frameId` 填的是**查看端正在显示的那一帧**。
被控端只在 `已发帧 - 事件帧 <= 3` 时才注入；否则丢弃并记一行日志。
理由：查看端看到的永远是若干帧之前的画面，如果被控端画面已经往前走了很多帧，
那个坐标对应的界面可能早就变了，这种操作落到错误的界面上比不执行更糟。

## 实测验证（三层，都有客观证据）

### 1) 捕获 → 归一化 → 转发（端到端）

在覆盖窗口内移动光标，被控端日志逐条对上（覆盖窗口左上 (206,243)、尺寸 1312x738）：

| 光标位置 | 窗口内坐标 | 归一化（被控端实测） | 手算校验 |
|---|---|---|---|
| (662,512) | (456,269) | (11397,11959) | 456/1311×32767=11398 ✓ |
| (1012,692) | (806,449) | (20145,19962) | 806/1311×32767=20147 ✓ |
| (742,672) | (536,429) | (13396,19073) | 536/1311×32767=13398 ✓ |
| (1042,572) | (836,329) | (20894,14627) | 836/1311×32767=20897 ✓ |
| (802,732) | (596,489) | (14896,21740) | 596/1311×32767=14899 ✓ |

同一时刻 `事件帧=451 已发帧=453` —— 查看端画面只落后 **2 帧**，守卫正确放行。

### 2) 帧号守卫

合成 1 个"最新"事件（`frameId=0xFFFFFFFF`）+ 2 个陈旧事件（`frameId=0`）：

```
[控制] 注入 kind=0 归一化(16384,16384) 事件帧=4294967295 已发帧=482 SendInput=1 err=0 光标=(80,80)
[控制] 丢弃陈旧输入：事件帧 0，当前已发 499（差 499 > 窗口 3）
[控制] 丢弃陈旧输入：事件帧 0，当前已发 500（差 500 > 窗口 3）
```

### 3) 结构布局自检

`INPUT` 的布局一旦被 `#pragma pack` 之类搞坏，`SendInput` 仍会返回 1，但字段会被系统按错误偏移读取
（表现就是"注入成功却没效果"）。所以被控端第一次注入时会打一行自检：

```
[控制] 自检 sizeof(INPUT)=40  sizeof(MOUSEINPUT)=32  offsetof(mi)=8  offsetof(mi.dwFlags)=20
```

与 Windows 期望一致（x64：INPUT 40 字节、dwFlags 在偏移 20）。

## ⚠️ 必须记录的环境限制：本 harness 里原生 exe 的 `SendInput` 不生效

**现象**：被控端 `SendInput` 返回 **1**、`GetLastError()=0`，但**注入后立刻 `GetCursorPos` 读回，
光标纹丝不动**；换成相对移动（不依赖坐标映射）也一样。

用最小程序把变量压到最低（[`build/inject-selftest.cpp`](../build/inject-selftest.cpp)，约 20 行，
不碰 D3D/MF/Winsock，只调 `SendInput`）：

| 调用方 | 结果 |
|---|---|
| PowerShell（harness 自己的进程） | ✅ (80,80) → **960,540** |
| 最小 C++ exe（**前台**运行） | ❌ `SendInput=1 err=0`，光标不动 |
| 最小 C++ exe（后台任务里运行） | ❌ 同上 |

**结论**：这是**本 harness 对"被拉起的原生进程"的限制**，不是代码缺陷 ——
和之前发现的"原生 exe 写不了工作区外路径（UnauthorizedAccessException）"是同一类现象。
PowerShell 的 `SendInput` 正常，说明**不是环境不支持注入**，而是**这些被拉起的原生进程的注入被静默吞掉**。

**影响**：
- 产品在真实机器上不受影响（`SendInput` 是最标准的注入方式）。
- 但**"注入有没有真的移动鼠标"这件事，在这个环境里无法端到端验证**。
  能验证到的是：捕获 → 归一化 → 转发 → 帧号守卫 → `SendInput` 被系统接受（返回值 + 结构布局 + 参数数值）。
- **建议**：在真实机器上跑一次 `build\inject-selftest.exe`（一分钟），
  它的输出会直接告诉你这台机器能不能注入 —— 这是远程控制能用与否的前提。

## 键盘（同日补上）

### 实现

- **被控端**：`InputEvent.kind = kInputKey` → 用 `KEYBDINPUT` 注入（`wVk` 给虚拟键码、
  `wScan` 由 `MapVirtualKeyW` 映射、`KEYEVENTF_KEYUP` 表示抬起）。
- **查看端**：覆盖窗口是 `WS_EX_NOACTIVATE`（**永不抢焦点**），所以**收不到 `WM_KEYDOWN`** ——
  只能装**全局低级键盘钩子**（`WH_KEYBOARD_LL`）。钩子**只转发、不吞键**（结尾照常
  `CallNextHookEx`），本地该收到的键一个不少。
- **默认关闭**：要显式加 `--remote-keyboard`（隐含 `--remote-control`）才装钩子。
  这正是设计文档"键盘开关默认关"的落地方式 —— 全局键盘钩子本身就是键盘记录能力，
  不能默认打开。原型应用目前只传 `--remote-control`，**键盘开关要等授权 UI 一起做**。

### 验证：注入这一侧 ✅，捕获那一侧在本 harness 里 ❌

**① 键盘注入（被控端）—— 用合成包验证通过**：

```
[控制] 注入 kind=3 归一化(0,0) vk=124 事件帧=4294967295 已发帧=363 SendInput=1 err=0   ← F13 按下
[控制] 注入 kind=3 归一化(0,0) vk=124 事件帧=4294967295 已发帧=380 SendInput=1 err=0   ← F13 抬起
[控制] 丢弃陈旧输入：事件帧 0，当前已发 396（差 396 > 窗口 3）                          ← 陈旧按键被拦
注入键盘事件 2 个（含按下与抬起）
```

（`vk=124` = `0x7C` = F13；按下/抬起靠 `flags` 的 `kInputDown` 区分。）

**② 键盘捕获（查看端）—— 本 harness 里收不到任何回调**：

| 步骤 | 结果 |
|---|---|
| 查看端装钩子 | `[信息] 键盘转发: 已装低级键盘钩子（全局；只转发不吞键，本地照常收到）` |
| 注入 4 次按键（F13/F14 各按下+抬起） | 查看端汇总：**`键盘钩子收到按键 0 个`** |
| 同一批按键，改由 **PowerShell 自己**装钩子观察 | **收到 2 次回调** |
| 按键注入本身是否生效（CapsLock 状态） | `OFF → ON → OFF` —— **生效** |

所以：环境支持键盘注入、也支持低级键盘钩子，**但被拉起的原生进程装的钩子收不到回调**。

### 这条边界现在很清楚了

| 能力 | PowerShell（harness 自己的进程） | 被拉起的原生 exe |
|---|---|---|
| 写工作区外路径 | ✅ | ❌ `UnauthorizedAccessException` |
| `SendInput` 鼠标/键盘注入 | ✅ 真的生效 | ❌ 返回 1 但无效 |
| `WH_KEYBOARD_LL` 全局键盘钩子 | ✅ 收到回调 | ❌ 装上但 0 回调 |
| 自己窗口的消息（`WM_MOUSEMOVE` 等） | — | ✅ 正常 |

看起来 harness 对这些进程限制了"影响整个桌面"的能力（注入输入、全局钩子、越界写盘），
只允许它们操作自己的窗口。**这是合理的安全边界，不是代码缺陷**。

### 结论

- 键盘这条链路的**协议、帧号守卫、注入调用**都已验证；**捕获能否工作只能在真实机器上确认**
  （真机上装钩子后按几个键，看被控端日志有没有 `注入 kind=3`）。
- 这也是为什么**键盘必须默认关闭**：在真实机器上它是一条全局键盘记录通道，
  必须由用户显式授权（设计文档 §9.5），并配"停止控制"的全局快捷键。

   —— 键盘的开关也要一起做（原型应用目前只传 `--remote-control`）
2. **点击穿透策略**：覆盖窗口现在会吃掉鼠标事件 —— 这**正是**远程控制需要的机制；
   等"本地操作 vs 远程注入"的区分做出来之后再决定默认行为（设计文档 §9.5.5）
3. **多显示器 / 负坐标**：归一化按虚拟桌面走（代码已带 `MOUSEEVENTF_VIRTUALDESK`），但只在
   1920x1080 单屏上实测过
