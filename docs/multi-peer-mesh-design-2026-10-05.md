# 多人共享（mesh 媒体）设计稿

> **【2026-10-06 更正】** 本文里多处「`run-checks.py` 5 项全 PASS / 全绿」是**当时**（2026-10-05）的事实。
> 现在 `build\run-checks.py` 是 **25 项**（`release` 模式修复前 9 项），以脚本实际输出为准。

> **触发**：2026-10-05 用户确认需求 —— **要"3 人及以上同时看同一路共享"**。
> 现状是 1:1 媒体（单 PeerConnection），房间里第二位及以后的成员拿不到媒体，做不到这件事。
> **本文件只做设计，不改代码**；动手前请你过一眼第 4、5 节的取舍与分步。

## 1. 验收标准（先说清"做成什么样算成"）

| # | 标准 | 怎么验（客观） |
|---|---|---|
| 1 | 房间里 **3 个实例**，A 共享屏幕，**B 和 C 同时看到 A 的画面** | 三个实例日志：B/C 都有"对方开始共享屏幕"+ 帧计数在涨；各抓一张显示区截图，非黑率 > 60% |
| 2 | 任意一方**中途加入**时，若当时有人在共享，**也看得到** | 先 A 共享，再起 C；C 的日志应出现"对方开始共享屏幕"，而不是像现在这样什么都没有 |
| 3 | 有人**重连**（新 id）后，其它人**不受影响**，且共享方的新链路**自动带上屏幕轨** | 杀 B 再起 B2：A↔C 链路不断，B2 能看 A 的共享 |
| 4 | 1:1 的既有功能**不回归** | `--selftest-host/--selftest-join` 双机自测仍通过；`run-checks.py` 5 项全 PASS |
| 5 | 不再有"看起来连上了、其实什么都没通" | 应用日志里不再出现"对端=N 但拿不到媒体"的静默情况；界面显示"正在与 X 共享/观看" |

## 2. 现状（全部实测过）

- `call.html` 里媒体状态是**单数**：`state.pc`（一条 PeerConnection）、`state.remoteId`（一位对端）、
  `chatChannel`（一条聊天通道）。`ensureLink()` 开头 `if (state.pc) return true;` —— 第二位对端被直接忽略。
- 房间名单是**多人**的（`state.peers` Map），所以应用侧会显示"对端=2"、按钮可点 → **误导**。
- 信令中继**已经**支持多人：按 `to` 单播、找不到就广播；2026-10-05 已补上 `from = 发送者 id`
  （`SignalingServer.cs` 的 `AddFrom()`），所以"这条消息属于哪位对端"现在**判断得出来**了。
- 应用侧：`--selftest-host/--selftest-join` 双机自测已通过；`link-busy` 会把"1:1 限制"如实写进日志。

## 3. 设计总览

```
                       ┌──────────────── 应用（C# / WinUI）────────────────┐
                       │ 观看状态：当前显示哪位共享者的画面（单画面 UI）        │
                       │ 原生视频通道：贴在自己窗口上方（与本次改动无关）        │
                       └───────────────▲───────────────────────────────────┘
                                       │ post: remote-screen-started/stopped(+peer)
                       ┌───────────────┴───────── call.html（页面）─────────┐
                       │  state.links: Map<peerId, PeerLink>                │
                       │    PeerLink = { pc, chat, screenSenders[], video }  │
                       │  本端 screenStream（唯一一路采集）                  │
                       │    → 每个 PeerLink 都挂上这条轨（扇出）              │
                       │  远端画面：每个 PeerLink 一个 <video>（只显示最新共享者）│
                       └───────────────┬───────────────────────────────────┘
                                       │ 信令（已支持多人：按 to 单播 + from）
```

**核心改动**：`state.pc` → `state.links`（按对端一条链路）。
共享是**一路采集、多路扇出**；观看是**多路接收、单路显示**。

## 4. 关键取舍（这几条请你确认）

| # | 决定 | 理由 |
|---|---|---|
| **D1** | **界面仍一次只显示一路远端画面**（最新开始共享的那位），不做 N 宫格 | 你的需求是"3 人都能看到同一路共享"，不是"一个人同时看 3 路"。这样 UI 几乎不用改，风险集中在页面。以后要 N 宫格再单独做。 |
| **D2** | **音频/通话仍保持 1:1**（与当前选中的那位对端） | 多人混音是另一件事（要混音、要防啸叫、要说话人指示）。本次只解决"共享画面多人可见"。 |
| **D3** | **不改信令服务器**（除了已完成的 `from`） | 它本来就按 `to` 单播、名单多人；改到页面里就够。 |
| **D4** | **原生视频通道不动** | 它是"贴在自己窗口上方的覆盖窗口"，与页面里的 WebRTC 媒体是两条独立的显示路径。 |
| **D5** | **保留 1:1 的语义**：两个人在房间时，行为与今天完全一致 | 降低回归面；多人只是"多了几条 PeerLink"。 |

### S2（按 from 路由）+ S3（共享扇出）—— 用户需求已达成

**改了什么**（`call.html`）：

1. `onOffer` 重写为**按 `from` 路由**：同一位对端 → 在它自己那条链路上重协商；**新对端 → 新建一条链路**
   （不再"不同对端就忽略"）。新链路只承载媒体；聊天/音频仍挂主链路（D2/S4）。
2. `ensureLink` 去掉 `if (state.pc) return true`：改成按对端查（`linkOf(remoteId)`），没有就新建 —— 这是 mesh 的**发起侧**。
3. `welcome` 时对**每一位**已在房间的对端建链（原来只连"第一位"，实测导致第三人连到第二位而不是共享方，
   于是永远看不到共享）。
4. `onAnswer` / `onRemoteIce` 也按 `from` 路由到对应链路。
5. **共享扇出**：`startScreenShare` 给所有链路挂屏幕轨并各自重协商；`stopScreenShare` 对所有链路 replaceTrack(null)；
   共享期间新加入的链路，在**应答之后**用一次重协商 offer 把屏幕轨推过去。
6. `hangup` 关闭**所有**链路（原来只关主链路，多余的会变幽灵）。
7. 共享前先补齐链路（兜底那些还没建上的对端）。

**踩到并修掉的一个真 bug（顺序问题）**：一开始把 `addTrack(屏幕轨)` 放在 **answer 之前** ——
WebRTC 的 answer **不能**加 offer 里没有的 m-line（对方的 link offer 只含音频），所以那条轨根本没协商上，
中途加入的人永远看不到画面。改成"先应答，再 addTrack + 发重协商 offer" ✓

**验收证据（三实例，A 共享 / B、C 观看）**：

```
A: 14:59:01 [链路] 注册表 1 条：5ddc07d6 → 【共享周期测试】① 开始共享
A: 14:59:02 [链路] 注册表 2 条：5ddc07d6,6e1170f8        ← 第二条链路建起来了
A: 14:59:11 【共享周期测试】② 停止共享
B: 14:59:01 对方开始共享屏幕；[链路] 注册表 2 条：ada6ffd5,6e1170f8
C: 14:59:02 [链路] 注册表 2 条：ada6ffd5,5ddc07d6（都 connected）
C: 14:59:02 对方开始共享屏幕
C: 14:59:02 [按钮] 对端=2 … 看对方=True
C: 14:59:07 收到画面帧 64 帧 (320×180)                    ← ★ 真的在收画面
```

**回归**：双机自测 8 步全跑完（`全部步骤结束（共 8 步）`），两份日志里 `失败/未建立/没收到/未就绪` **0 条**；
`run-checks.py` 5 项全 PASS。

**S4–S6 仍未做**：每对端聊天通道（现在聊天仍只走主链路）、远端多路画面（现在"最新共享者优先"）、
应用侧把"正在观看"改成共享者集合。按 D1/D2 这些是后续增强，不影响"3 人同时看同一路共享"这条需求。

### S6（应用侧共享者集合）+ mesh 健壮性修复（2026-10-05 晚）

**改了**：

1. **S6**：页面把"谁在共享"带上（`remote-screen-started/stopped/switched` 都带 `peer`）；
   应用侧从布尔 `_viewingRemoteScreen` 改成 **`HashSet<string> _sharingPeers` + `_lastSharer`**：
   还有人在共享就保持显示（标题换成还活着的那位），**一个都不剩才收起**。
   （旧逻辑是"任何一位停止就收起"，两人同时共享时会误收。）
2. **页面通知带 peer**：`ontrack`、`track.onended`、`removetrack`、`screen-stop-notify` 四处都带上对端 id。
3. **`peer-left` 只拆这一位对端的链路**（原来 `if (state.remoteId === msg.id) await hangup(...)` 会把
   **所有**链路一起关掉 —— 3 人房间里走掉一个人，剩下的人也跟着断、共享画面也没了）。
   主链路走了就 `adoptPrimaryAliases()` 把别名切到还活着的那位（这个函数之前**定义了从没被调用**），
   并新增页面通知 `link-switched`；一条都不剩才 `hangup`。

**验收（三实例：A 共享、B 与 C 观看，中途杀掉 A 的主对端 B）**：

```

A: 15:04:10 [链路] 注册表 2 条：70a1d3c6,cfa23cf5      ← C 加入，第二条链路
A: 15:04:19 [链路] 注册表 1 条：cfa23cf5               ← B 走 → 只拆那一条
A: 15:04:19 [链路] 主链路切换为 cfa23cf5（共 1 条）      ← ★ 以前这里会 hangup 全部
C: 15:04:10 对方开始共享屏幕（8e75e5），当前共享者 1 位  ← S6 集合计数
C: 15:04:15 收到画面帧 64 帧 (320×180)                 ← 正常收画面
C: 15:04:18 [界面] 没有人在共享了，隐藏共享显示区       ← 集合空 → 收起
```

**注意（诚实标注）**：B 是在 A 停止共享后 1 秒被杀掉的，所以"**B 离开的同时 C 还在收画面**"
这个并发场景没有直接抓到；但同一段代码路径已经验证（A 的注册表从 2 条变 1 条、剩下的正是 C 的链路，
C 的链路完全没被动过）。

**回归**：双机自测 8 步全跑完、失败迹象 0 条；`run-checks.py` 5 项全 PASS；页面 JS 语法自检 OK。

### S4（每对端聊天）为什么先不做

聊天现在是**一条全局通道**（`chatChannel` = 主链路的通道），界面也只有一个聊天视图。
3 人房间里，第三个人的消息需要"**跟谁聊**"这个选择 —— 那是**界面设计**（成员列表 + 会话切换），
不是纯技术改动。按 D2 的取舍先保持 1:1 聊天，等你要多人聊天时再单独定 UI。
