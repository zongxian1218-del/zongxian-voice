# 远程控制授权（设计文档 §9.5 落地）（2026-10-05）

## 这一版做了什么

被控端第一次收到远程输入时**弹出授权窗口**，并严格遵守设计文档那几条硬要求：

| 设计要求 | 实现 |
|---|---|
| 默认焦点在「拒绝」 | 「拒绝」是 `BS_DEFPUSHBUTTON` 且 `SetFocus` 到它 —— 截图里能看到焦点环 |
| 30 秒无响应即拒绝 | 窗口内实时倒计时，归零自动走拒绝路径（`--auth-timeout` 可改，测试用） |
| 「键盘」开关默认关 | 勾选框「允许键盘输入（默认关）」默认不勾；未勾选时按键事件被丢弃并计数 |
| 被控时红色横幅常驻顶部 | `ZxControlBanner`：全屏宽 44px，`WS_EX_TOPMOST｜NOACTIVATE`，纯红底白字 |
| 「停止控制」一击生效、不二次确认 | 红条上的按钮直接调 `StopByUser()`，没有任何确认步骤 |
| 停止控制有全局快捷键 | `RegisterHotKey` **Ctrl+Alt+End**（实测注册成功，见下） |
| 未授权不得注入 | 未授权期间的输入**一律丢弃**，只计数不注入 |

**新增协议**：`kTypeControlState`（被控端 → 查看端，载荷 1 字节）。
被控端每次状态变化都通知查看端，查看端收到"已拒绝/已被停止"就**停止继续发送输入**
（否则控制通道会一直被无用地占着）。

状态：`0=等待决定 / 1=已允许 / 2=已拒绝（含超时）/ 3=已被本人停止`。

**开关**：`--remote-control` **默认就要授权**；`--no-auth` 只给自动化测试用（日志里会打警告）。
`--auth-timeout <秒>` 用于把等待时间调短。

## 本轮修掉的 4 个 bug（2026-10-05，测试之后）

补测过程中暴露出 4 个真问题，都已修 + 有实测证据：

### A. 拒绝/超时/停止之后，**新的控制请求永远不会再弹窗**（进程内永久锁死）

原来 `Ask()` 只在状态是 idle 时触发；一旦被拒，`state_` 就停在 denied/stopped，
后续输入只会被丢弃 —— 用户点错一次，这个功能到进程结束都废了。

修法（`ControlAuth::ShouldReask`）：
- **换了请求方**（IP 或端口不同）→ 立即可以再请求；
- **同一个人** → 过冷静期（`--auth-cooldown`，默认 30 秒）后可再请求，免得被反复弹窗骚扰。

实测（`--auth-timeout 3 --auth-cooldown 30`，三个来源依次请求）：

```
[授权] 已弹出授权窗口 ...                                      ← 来源1 第一次
[授权] 3 秒无响应 → 自动拒绝
[授权] 已记录：30 秒内同一请求方不会再次弹窗（换了请求方则立即可以再请求）
[授权] 已被拒绝/已停止，输入被丢弃（累计 1 个）                 ← 同一来源、冷静期内：不再弹窗 ✓
[授权] 已**再次**弹出授权窗口（上次是拒绝/被停止）               ← 换来源(50956)：立即再弹 ✓
```

### B. 被控端换会话（重启）后，查看端仍以为"已被拒绝"，**永远不再发输入**

查看端把 `denied/stopped` 记为永久阻断；被控端重启（新的 sessionId）后它依然不发 —— 换了会话却不恢复。

修法：在检测到新会话（`sessionSwitches` 增加）时复位授权状态。

实测（查看端单独跑，用合成包制造"被拒 → 换会话"）：

```
[控制] 已转发输入 ...（累计 1）
[控制] 被控端授权状态: 已拒绝 —— 查看端停止发送输入
[控制] 被控端已拒绝/已停止，输入不再发送（后续同类丢弃只计数）
[信息] 检测到新会话 sessionId=0x3333（第 1 次），重组器已重置
[控制] 被控端换了会话，授权状态已复位（可以重新发起控制请求）    ← 复位 ✓
[控制] 已转发输入 ...（累计 50）                              ← 恢复转发 ✓
```

### C. 查看端有 5 处**静默 return**，导致"没转发"时毫无线索

`SendInputEvent` 里"控制通道没就绪 / 还没学到被控地址 / 取客户区失败 / 客户区退化"
都是直接 return，什么都不留。**上一轮排查正是被这种静默丢弃带偏的。**

修法：每条原因各记一次（不刷屏），并给前 3 次 `WM_MOUSEMOVE` 留痕。
实测（只开查看端、不开被控端）：

```
[控制] 覆盖窗口收到鼠标移动 #1 客户端坐标(250,220) 客户区 1280x720
[控制] [!] 还没收到被控端的画面，尚不知道往哪发输入（只记这一次）
```

（顺带确认了坐标映射正确：`SetCursorPos(500,400)`、覆盖窗口左上 (250,180) → 客户端 (250,220)。）

### D. 停止/拒绝后的输入被计入"尚未授权"，日志口径误导

修法：拆成 `inputAwaitingAuth`（等待/未获授权）与 `inputBlockedByAuth`（已被拒绝/已停止），
汇总分别打印。实测输出见 A 的汇总行：`因已被拒绝/已停止被丢弃 1 个（要重新控制需再次请求）`。

### 三个被排除的"疑似 bug"（同样重要）

| 疑似问题 | 结论 | 依据 |
|---|---|---|
| 查看端在对端消失后会卡住/退出 | **不成立** | 查看端 40 秒跑满：39 条每秒统计 + 完整收尾报告；发送端 14 秒就退了 |
| "包石沉大海"是 `SIO_UDP_CONNRESET` 导致 | **不成立**（本机） | 时序复现实验里 4 个包全部正常收到，ICMP 只影响一次 drain；防护仍已加上 |
| 上一轮"查看端没转发输入" | **测试时序错误** | 那次是查看端已被我杀掉，阶段 2 面对的是不存在的查看端 |

**另一个反复咬人的环境坑**：Windows 回环 UDP **每个阶段实际发出的第一个数据报会丢**
（文档早已记录）。这轮又踩了一次 —— 单个合成媒体包正好是那"第一个"，所以会话切换没触发；
连发两个才验出来。

## 补测：键盘未授权时按键被丢弃（这条原来是空的）

### 测试方式（确定性，不依赖"人点得准不准"）

用被控端自己的合成输入包触发弹窗，再用 [`build/auth-click.py`](../build/auth-click.py)
以**真实点击**去点按钮：

```powershell
# ① 合成鼠标包 → 弹窗
python build\send-input-packet.py 41000 0 16384 16384 4294967295
# ② 点「允许」（键盘勾选框保持默认不勾）
python build\auth-click.py allow
# ③ 鼠标移动 / 按键 / 鼠标左键 各一个
python build\send-input-packet.py 41000 0 8000 8000 4294967295
python build\send-input-packet.py 41000 3 0 0 4294967295 0 0x7C 8      # F13 按下
python build\send-input-packet.py 41000 1 8000 8000 4294967295 0 0 9    # 左键按下
```

### 结果

```
[授权] 本人点了「允许」（仅鼠标，键盘未勾选）
[控制] 注入 kind=0 归一化(8000,8000) vk=0 事件帧=4294967295 已发帧=359 SendInput=1   ← 鼠标移动：放行
[授权] 丢弃按键 vk=124：授权时没有勾选「允许键盘输入」                                ← 按键：明确丢弃
[控制] 注入 kind=1 归一化(8000,8000) vk=0 事件帧=4294967295 已发帧=398 SendInput=1   ← 鼠标左键：放行

注入鼠标事件 2 个（其中移动 1，SendInput 被拒 0）
注入键盘事件 0 个
因等待/未获授权被丢弃 1 个（授权状态下不会注入）
因键盘未授权被丢弃 1 个（授权窗口里没勾「允许键盘输入」）
最终授权状态: 1（0=等待 1=已允许 2=已拒绝 3=已被本人停止）
```

**顺带改进**：这次给"静默丢弃"补了日志（未授权丢弃只记第 1 次和每 100 次；键盘未授权丢弃记前 2 次和每 20 次）——
之前正是"丢了但没有任何记录"让排查绕了远路。

### 一个必须记下来的坑：测试脚本要先声明 DPI 感知

`auth-click.py` 一开始报的按钮坐标是 (905,489)，而授权窗口实际在物理坐标 (730,420)、
「允许」应在 ≈(1123,637) —— 比值正好 **0.8**。

原因：**这台机器是 125% 缩放**（1920×1080 → DPI 不感知的进程看到虚拟化的 1536×864）。
python 默认不声明 DPI 感知，于是 `GetSystemMetrics` 与 `GetWindowRect` 全被虚拟化，
坐标归一化按 1536 算 → 点击实际落到 `x*1.25` 的位置，**打在窗口空白处**（表现为"点了没反应"）。

修法（第一时间调用）：

```python
ctypes.windll.shcore.SetProcessDpiAwareness(2)   # PROCESS_PER_MONITOR_DPI_AWARE
# 或 ctypes.windll.user32.SetProcessDPIAware()
```

修完后 `auth-click.py` 报的按钮中心 (1123,637) 与手算完全一致，点击一次命中。
**这也解释了之前两次"看起来点了却没生效"**。

## 设计取舍（为什么这么做）

- **为什么授权放在被控端而不是查看端**：被控的是别人的机器，只有本人能同意。
- **为什么必须在消息循环线程建窗口**：发送端主循环里加了一句 `auth.Poll()`（泵消息 + 走倒计时），
  否则窗口不响应、倒计时也不走。
- **为什么状态要回传**：没有回传时，查看端在对方拒绝后仍会一直发输入 —— 既浪费带宽，
  也让"已拒绝"这件事在查看端完全不可见。
