# `dist/` 卫生与发布物规范（2026-10-05）

> **起因**：接手项目时列的"**比 bug 更危险的三件事**"里就有"dist 一团乱"——
> 同一个发布线躺着好几个版本的包、日志混在里面、打包产物比源码老十几个小时。
> 这类问题**不报错**，只会让人发错包；而 `resources.pri` 那次启动崩溃就是同一类问题
> （产物缺一件东西，谁都没发现）。这份文档定规则，`run-checks.py` 里加硬闸门。

## 2. 规则（`run-checks.py` 会逐条查）

1. **每个 WinUI 应用目录旁边必须有 `resources.pri`**
   （缺了启动即崩 `0xc000027b`，见 `check_app_pri` 的注释）。
2. **每个 WinUI 应用目录必须有 `BUILD-INFO.txt`**：commit、构建时间、配置、重建命令。
   由 `build\build-winui-cs.cmd` 自动写入 —— 没有它就无法判断"这个包是哪次构建"。
3. **同一发布线只留最新一个包**：`棕仙语音-测试版-vNN.zip` 只允许存在一个（最新的）。
4. **不允许中间产物与日志**：`.pdb / .obj / .ilk / .log / .exp / .lib` 一律不许进 `dist/`。
   **例外**：`dist\winui\.webview2\**` —— 那是 WebView2 自己的浏览器配置目录，
   里面的 LevelDB `000003.log` 等是它的运行时文件（第一版规则在这里误报了 9 条，已修正）。
5. **不允许重复副本**：文件名带"副本"或" - Copy" 的一律不合格。
6. **只挪不删**：不合格的东西移到 `build\dist-quarantine-<日期>\`（该目录在 `.gitignore` 里）。
   删掉就再也说不清"上次发的是哪个包"。

## 5. 怎么用

```powershell
python build\run-checks.py          # 全跑：25 项 = 3 构建 + 界面自检前置 --no-click + 界面自检（模拟键鼠）
                                    #        + 8 条守卫（pri / dist 卫生 / 媒体·探针一致性 / 脚本名字绑定
                                    #          / 残留规则 / 界面控件名 / RELEASES 表格结构 / cmd 行尾）
                                    #        + 传输层 6 阶段
python build\run-checks.py release  # 发版严格模式：同为 25 项（2026-10-06 修复：原 release 漏跑传输层）
python build\run-checks.py build    # 只跑构建 + 两条界面自检 + 8 条守卫 = 13 项（不含传输层）
```

> **【2026-10-06 更正】** 本节 2026-10-05 写的「6 项：4 项构建 + pri 守卫 + dist 守卫」**已作废**。
> 项数以 `build\run-checks.py` 实际输出为准（数法：构建 `:597,604,611`；界面自检 `:629,637`
> 与缺 smoke 时的 `:650`；8 条守卫 `:652-659`；传输层 `:664-692` ⇒ 正常路径 3+2+8+1=14）。
> 另：环境中止（用户在用电脑/弹窗）时 `run-checks` **退出码 3**，含义是"无法验证"，不是产品 FAIL。

守卫失败时的修法：按 `[问题]` 逐条处理 —— 陈旧/重复物挪到隔离区，
应用目录缺 `BUILD-INFO.txt` 或 `resources.pri` 就重跑 `build\build-winui-cs.cmd`。

## 7. 追加（同日）：发布物清单 + 两条"可靠判据"

### 一个被否掉的判据（值得记下来）

最初想加"**产物时间 vs 源码最后改动**"的检查。跑出来 A 线发布物"落后 20.4 小时"，看着很吓人，
但一查就发现是**假警报**：本仓库是 **2026-10-05 才初始化**的，
`src/swiftdrop` 只有一次提交（`66ae24e`，10-05 10:40 = 我建基线那次），
而源码是 10-04 写的 —— **提交时间根本不代表作者时间**。
所以这条判据**没有写进守卫**（一个会误报的守卫比没有守卫更糟）。

### 换成两条不会骗人的判据

| 判据 | 做法 | 为什么可靠 |
|---|---|---|
| **交付网页逐字节一致** | `dist\swiftdrop.html`（入库的源素材）与 A 线便携版内两份 `swiftdrop.html`（根 + `_internal`）比 SHA-256 | 内容相等是事实，与时间无关。今天实测三份**完全一致** ✅ |
| **发布物清单双向核对** | `dist\RELEASES.md` 登记每个顶层项；守卫查"顶层都登记了"且"登记的都还在" | 逼着人登记/注销；`dist` 里多出一个没来源的文件会立刻被发现 |

**验证（注入故障 → 抓得住）**：

```
注入 ①便携版里改坏 swiftdrop.html ②dist 里塞 __probe.tmp
  → [问题] 网页与源码不一致（棕仙的传输软件\swiftdrop.html 与 dist\swiftdrop.html 不同）
  → [问题] __probe.tmp 没在 dist\RELEASES.md 里登记
  → ---- FAIL: dist 卫生
还原 → ---- PASS: dist 卫生
```

### 顺便核清的事实与遗留

- **A 线的网页部分与源码一致** ✅（上面那条判据）。
- A 线的 exe/zip（安装包、自解压、portable zip）**构建于本仓库首次提交之前**，
  **没有溯源记录** —— 要把"A 线发布物与源码一致"变成可核对事实，
  得重跑一次 A 线打包链并在产物旁写 `BUILD-INFO.txt`。已写进 `dist\RELEASES.md` 的待办。
- `棕仙语音-测试版-v22.zip`（10-05 10:09）**落后于当天下午的源码**（原生视频进主应用、多人共享等）；
  `dist\winui\` 已刷新到当前版。~~下次重打包应出 v23。~~【2026-10-06 事实：此后包号一路到 v36，
  而 **v36 已作废**（陈旧页面 + 测试残留，挪进隔离区）、v37 被发版闸门拦住 —— 本句的 v23 预测
  仅作历史，现行包状态见 `docs\handoff-next-session.md` §1】
