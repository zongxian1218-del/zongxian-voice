# 渲染路径验证：解码结果上屏（2026-10-05）

## 目标

接进 WinUI 之前，先验证最后一个没跑过的环节：**解码出来的帧怎么变成屏幕上的画面**。
按一贯做法，先在独立窗口里跑通，再换成 WinUI 的 SwapChainPanel —— 一次只引入一个新变量。

## 结果

```
收包总数        : 7360 共 8,866,163 字节
重组交付帧      : 330
分片不齐丢弃帧  : 0
XOR 校验救回    : 1 片
解码输出        : 330 帧
已上屏帧数      : 330 帧（窗口 1280x720）   ← 全部上屏
首包→首帧耗时   : 9.1 ms
解码延迟        : 平均 3.0 ms / 最大 14.6 ms
解码耗时        : 平均 3.44 ms/帧（预算 33.3 ms）
```

**逐帧对齐：重组 330 → 解码 330 → 上屏 330，零丢失、零积压。**

---

## 设计选择：BGRA 而不是 NV12 + 着色器

NV12 上屏通常要写 HLSL 做色彩空间转换，还要处理 NV12 纹理的双平面
（`ArraySize` 必须是 2，subresource 0 是 Y、1 是 UV），很容易出错。

改成让 libavcodec 的 `sws_scale` **直接输出 BGRA**，就只剩三步：

```
UpdateSubresource(上传纹理) → CopyResource(到后台缓冲) → Present
```

没有任何着色器代码。

**代价**：CPU→GPU 带宽从 3.1 MB/帧（NV12）涨到 8.3 MB/帧（BGRA），
1080p30 就是 250 MB/s。相对 PCIe 和内存带宽可以忽略，换来的是**不可能出错**的路径。

`DXGI_SWAP_EFFECT_FLIP_DISCARD` + `Present(0, 0)`（不做垂直同步，省掉最多 16ms）。

---

## 验证方式：不靠肉眼

窗口内容和真实桌面太像了，看着像不算证明。用**客观像素比对**：

预览窗口在 (40,40)，客户区在 (48,71)，它显示的应该是「采集到的屏幕左上角 1280×720」。
所以：

```
A = 屏幕截图 (0,0)-(1280,720)         ← 应该被显示的内容
B = 屏幕截图 (48,71)-(1328,791)       ← 预览窗口客户区
C = 屏幕另一块对照区域
```

第一次测量：`A↔B = 35.1`，`A↔C = 106.8` → **吻合度是对照组的 3 倍**，证明成立。

（第二次测量受桌面动画影响变成 60.3 / 94.8，比值仍有区分度但不那么干净。
更稳的判据是日志里的「已上屏帧数」，`PresentBgra` 在交换链无效时返回 false。）

另外截图里能看到**无限镜像效果** —— 预览窗口里显示着包含它自己的桌面 ——
这只会在"窗口正在显示实时的屏幕采集"时出现。

## 踩到的坑

| 现象 | 根因 |
|---|---|
| `C7568: 假定的函数模板 ComPtr 后面缺少参数列表` | **`using Microsoft::WRL::ComPtr;` 写在类内部**。这个坑在 `h264-decoder.h` 已经踩过一次，这次又犯了。必须放命名空间作用域 |
| `LNK2019 __imp_CreateWindowExW` 等 13 个 | 忘了链 `user32.lib` |
| **运行结果自相矛盾**（日志显示上屏 330 帧，结论却是"没有解出画面"） | **构建其实失败了**（`error C2065: "i" 未声明`），跑的是上一次的旧 exe。我把构建输出 `Select-Object -Last 6` 之后**没有读**，所以没发现 |

最后一条最值得记：**构建输出必须每次都看**。用旧二进制跑出来的结果会把你引向完全错误的结论 —— 这次我差点就去查"为什么上屏了却判定失败"这个根本不存在的问题。

（这个错误的来源是我用 PowerShell 字符串替换插入 `--topmost` 判断时，把 `for` 循环的花括号搞丢了。**改代码还是应该用 edit 工具，不要用字符串替换。**）
