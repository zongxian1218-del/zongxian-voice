## 包格式

固定 **32 字节包头**（`static_assert` 钉死），载荷上限 1200 字节 → 整包 1232 字节，稳在 1500 MTU 以下。

```
magic/version/type/flags/streamId  (5+3 字节，含对齐)
frameId                            (4)  单调递增，用于排序与缺口检测
fragIndex/fragCount                (4)  校验分片下标 = 数据分片数
timestampUs                        (8)  采集时刻，音视频共同时钟
totalFrameBytes/payloadSize        (6+2)
```

## 职责边界（这一条是踩坑换来的）

**传输层只做两件事**：把分片重组成完整帧、按 frameId 严格递增交付。
它**不判断**某帧能不能解码，也**不因为丢帧而停止交付**。

### 错误设计一：让传输层自己"等关键帧"

最初版本：丢帧后进入 `waitingKeyframe_` 状态，忽略所有非关键帧。

后果：这个状态和请求限速互相作用，**陷入长时间冻结**——丢一帧要等 200ms
限速周期，期间收到的帧全部丢弃。实测 **60 帧只交付 10~13 帧**。
更糟的是，它在等待期间不再检测新的丢失，所以永远不会重发请求，
如果那个被请求出来的 IDR 本身也丢了，链路就**永久卡死**。

### 正确设计：照常交付 + 如实报告缺口

```
Result {
    delivered        // 有一整帧可交付
    gapDetected      // 本帧之前有帧丢失（新的缺口）
    gapFrames        // 缺口跨了多少帧
    droppedIncomplete// 有帧因分片没到齐被丢弃
    parityRecovered  // XOR 救回了分片
    duplicate
}
needsKeyframe()      // 有未恢复的缺口，消费端据此请求 IDR
```

消费端（解码器）决定"缺口之后的非 IDR 帧不喂进去"。传输层不管这些。

## 四个真 bug 及其根因

### 1. 迟到的旧帧分片会重置当前组装状态

**症状**：交付 `60/60` 却同时报告 **58 次丢帧**——自相矛盾的数字。

**根因**：真实网络里跨帧乱序很常见（帧 N 的校验包在帧 N+1 开始组装后才到）。
旧包 `p.frameId != curFrameId_` 被当成「新帧」，把正在组装的 N+1 重置成 N，
于是 N+1 的后续分片又触发一次「新帧」，陷入 churn。

**修法**：
```cpp
if (haveExpected_ && p.frameId < expectedFrameId_) { ignored; return; }
if (assembling_ && p.frameId < curFrameId_)         { ignored; return; }
```
修完阶段 1 的丢帧数从 **58 → 0**。

### 2. 请求风暴 → 正反馈雪崩

每次丢帧都发关键帧请求，形成：
**请求 → 120KB 的大 IDR → 分片数暴涨 → 更多丢包 → 更多请求**

实测 60 帧内 44 次丢帧，码流涨到 3 倍。**两端都要限速**（各 200ms 一次）。

### 3. XOR 校验分片的下标会被误判越界

校验分片的 `fragIndex` 恰好等于**数据分片数**，用 `fragIndex >= have_.size()`
判断会把它当成越界丢掉。必须先判 `kFlagParity`。

### 4. `dataFragCount_` 不能从 `fragCount` 推导

启用校验时 `fragCount = 数据分片数 + 1`，而数据包里带的是同一个值，
按它推导会**多算一片，导致永远凑不齐**。只能按 `totalFrameBytes` 算。

## Socket 层的两个要点

1. **`SO_RCVBUF` 必须在 `bind` 之前设置**。Windows 上 bind 之后再设可能不生效，
   仍是默认 64KB。一个 IDR 帧约 130KB（109 个分片）瞬间冲到，必然溢出。
2. **接收端必须是独立线程**。最初把测试写成单线程「先发完 100 个包再开始收」，
   结果**第一个数据包就丢**——那是在测试一个不存在的场景。
   真实应用里接收端一直阻塞在 `recvfrom` 上持续收包。

## 关键数据

```
包头          32 字节        载荷上限 1200 字节      整包 1232 字节
IDR 帧        约 130 KB → 约 109 个分片
P 帧          8~40 KB    → 7~34 个分片
平均投递延迟  0.94 ~ 1.15 ms（回环）
XOR 开销      每帧 1 个包（IDR 约 +1%，P 帧约 +5%）
```

回环下也观测到**真实丢包**（偶发单分片丢失，多发生在突发首包），
XOR 校验能 100% 救回——这正是"轻量 FEC"的价值。
