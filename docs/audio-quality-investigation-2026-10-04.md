# 音质排查记录（W1 期间）

日期：2026-10-04
触发：用户反馈「音质有点差」，症状选了**四项全中**：
发闷细节丢失、金属音/机器人音、断续卡顿、声音偏小忽大忽小。

---

## 1. 先分清"测试方法的伪影"与"真实缺陷"

用户是在**同一台机器**上测的。同机双实例会产生**声学回环**：

```
实例A 扬声器播放 B 的音频 → A 的麦克风收回去 → 传给 B → ...
```

这个回路天然会产生用户描述的全部四种症状：

| 症状 | 回环下的成因 |
|---|---|
| 金属音/机器人音 | 降噪在处理回声残留 |
| 断续卡顿 | AEC 在双讲（double-talk）时削波 |
| 忽大忽小 | AGC 追着回声调增益 |
| 发闷 | 回声被当成噪声压掉，人声跟着受损 |

**所以同机测试听到的音质问题，不能直接当成产品缺陷。**
要判断真实音质，必须用不经过回环的手段 —— 见 §3 的录音自检。

---

## 2. 已确认并修掉的真实缺陷

### 2.1 码率只有 15 kbps（这是实实在在的问题）

实测通话栏显示 **15 kbps**。Opus 在 15 kbps 下语音明显发闷、齿音与气息声丢失。

**根因**：我没有设置任何码率参数，完全交给 WebRTC 的带宽估计。而它偏保守 ——
优先保连接稳定，不会主动为音质多花带宽。

**修法**：显式设置
```js
maxaveragebitrate=40000   // 抬到语音的"透明"区间
useinbandfec=1            // 轻微丢包用冗余恢复，而不是降码率规避
usedtx=1                  // 静音不发包，把带宽留给说话时
stereo=0                  // 单声道：带宽全用在单声道质量上
```
两处都做才可靠：`sender.setParameters()` 设发送端上限，
同时在 **SDP 的 fmtp 行**里改写 —— Opus 的真实工作点由协商结果决定。

> **踩坑记录**：第一次只加了 SDP 改写、**没加容错**，直接把通话打挂了。
> 日志停在「信令连接加入」之后什么都没有，双方再也连不上。
> 教训：**音质优化绝不该让通话失败**。现在 `boostOpusInSdp` 全程 try/catch，
> 任何异常都退回原始 SDP，并且改完会自检（必须仍含 opus rtpmap 与新码率）。

### 2.2 双重自动增益（直接对应"忽大忽小"）

「强力」档挂了 `DynamicsCompressor(threshold=-45, ratio=4)`，
而浏览器的 `autoGainControl` 此时**也是开的** —— 两套增益控制互相追，
听感就是声音忽大忽小。

**修法**：
- 「强力」档**关掉浏览器 AGC**（`autoGainControl: false`），只留软件链
- 把 ratio 从 4 降到 **1.8**、threshold 从 -45 降到 **-50**、knee 放宽到 **20**
  —— 只压底噪，不压人声。旧参数偏激进，是"发闷"的来源之一

## 3. 新增：单机可验证音质的录音自检

同机测试被回环污染，所以必须有**不经过对端**的验证手段。

**做法**：录下**本地麦克风经过处理链之后**的信号，存成 WAV。这样能：

- 直接听文件，对比「关 / 标准 / 强力」三档的差别
- 看客观指标：峰值、RMS、削波、静音占比、频谱分布
- 完全不依赖对端，单机即可复现

**入口**：
- 界面：通话栏「录音自检」按钮（录 3 秒）
- 命令行：`ZongxianVoice.exe --record-test`（脚本化，用于 CI）

产出落在 `dist/winui/recordings/mic-<档位>-<时间>.wav`。

### 3.1 首次实测结果（录音时无人说话）

```
格式: 1 声道 / 48000 Hz / 16 bit / 3.07 秒
峰值: -37.0 dBFS      RMS: -52.7 dBFS
直流偏移: 0.00000     削波: 0 个
静音块占比: 89.5%
频谱: 低频(0-300Hz) 61.2% / 中频(300-3k) 32.9%
      高频(3k-6k) 2.5% / 齿音(6k-12k) 1.6%
频谱质心: 1005 Hz
```

**解读**：
- **89.5% 是静音块 → 录音时没有语音输入**，所以这份数据无法判断真实音质。
  频谱质心 1005 Hz 落在语音典型区间（500~1500），说明**代码路径是通的**，
  录到的确实是环境声而非异常信号。
- **峰值 -37 dBFS 偏低**。正常说话时一个增益正常的麦克风应到 -20 ~ -10 dBFS。
  偏低意味着增益不足 —— 这是"声音小 / 发闷"的一个候选原因，**与码率无关**。

### 3.2 下一步该做的验证

录一段**正常音量说话**的样本，回答两个问题：

| 看什么 | 判据 | 指向 |
|---|---|---|
| 峰值 | 应 ≥ -20 dBFS | 明显更低 → 增益问题（系统麦克风音量 / AGC 被关掉） |
| 齿音能量（6k-12k） | 说话时应有可测量的占比 | 接近 0 → 被降噪或编码削掉了 → "发闷" |
| 静音块噪声底 | 「关」与「强力」对比应有明显差 | 差别很小 → 降噪没起作用 |

对比方法：切档位各录一次（文件名含档位），直接播放对比 + 跑同一个分析脚本。

## 4. 新增：麦克风电平表

界面上加了实时电平条。理由很实际：用户说「对方听不到我 / 声音小」时，
**第一步要判断的是本机到底有没有拾到音**，而不是先怀疑网络或编码。
没有电平表就只能靠猜。

削波时电平条变红（提醒调小），静音时变灰。

## 5. 待办

1. **需要用户提供一段"正常说话"的录音样本**，才能判定真实音质。
   当前所有音质结论都受限于"录音时无语音输入"。
2. 若确认是增益不足：考虑恢复浏览器 AGC（但那样会与软件链冲突），
   或改用 `GainNode` 做可控的固定增益补偿。
3. 用户反馈的另外三个症状（金属音、断续、忽大忽小）需要通过
   **两台真实机器**的测试才能区分是回环伪影还是真实缺陷。
   同机测试在这三项上没有诊断价值。
