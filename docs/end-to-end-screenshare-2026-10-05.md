# 端到端屏幕共享打通 + 延迟问题定位（2026-10-05）

## 已经打通的链路

**发送端**（`sender-probe.exe`）与**接收端**（`receiver-probe.exe`）通过自建 UDP 跑通：

```
DXGI 采集 → GPU 转 NV12 → NVENC H.264 → 自建 UDP 分片
   → 网络 → 重组 → XOR 校验 → H.264 解码 → NV12 画面
```

**实测数字（1080p30，本机回环）：**

| 项目 | 数值 |
|---|---|
| 收发帧数 | 180 帧发出 / 180 帧重组 / 180 帧解码 |
| 分片数据报 | 发送 3443 个，接收 3442 个（**只丢 1 个**） |
| 丢包恢复 | XOR 校验救回 1 片，**分片不齐丢弃 0 帧** |
| 缺口 | 0 次 |
| 码率 | 约 5.1 Mbps |
| 画面 | 3 张 BMP 存证，肉眼确认与源桌面一致 |

**"只丢 1 个数据报、被校验救回、0 帧丢失"** 是这轮最有说服力的数字 ——
说明轻量 FEC 在真实链路里确实在干活。

## 发现的问题：解码器固定引入约 900 ms 延迟

### 现象

接收端每秒统计显示，`已重组帧` 与 `已解码` 之间**恒定相差 27 帧**：

```
[ 5.0 秒] 已重组帧 24   已解码 0    解码延迟 0 ms
[ 6.0 秒] 已重组帧 54   已解码 27   解码延迟 903 ms
[ 7.0 秒] 已重组帧 84   已解码 57   解码延迟 916 ms
[ 8.1 秒] 已重组帧 115  已解码 88   解码延迟 903 ms
[ 9.1 秒] 已重组帧 145  已解码 118  解码延迟 903 ms
```

27 帧 × 33.3 ms ≈ **900 ms**，与「首包→首帧耗时 901.6 ms」完全吻合。
差值恒定不变，说明这是**固定管线深度**，不是来不及处理堆积出来的积压。

### 已排除的原因

| 假设 | 证据 | 结论 |
|---|---|---|
| 解码器算力不够 | 解码耗时 **1.39 ms/帧**，预算 33.3 ms，只用 4% | ❌ 排除 |
| 有 B 帧需要重排序 | 向 NVENC 下发 `B 帧数 = 0`，返回 `E_INVALIDARG`（该 GUID 不支持），但 NVENC 默认本就不开 B 帧 | ❌ 不太可能 |
| 参考帧数太多导致 DPB 过大 | 下发 `MaxNumRefFrame = 1` 返回 `S_OK`，**自写 SPS 解析确认 `max_num_ref_frames = 3`**（默认是 16，确实降下来了） | ❌ 已生效但无效 |
| 解码器线程数按核数开 | 尝试 `CODECAPI_AVDecNumWorkerThreads = 1` → `E_INVALIDARG`；且本机 16 逻辑核 / 10 物理核，与 27 也对不上 | ⚠️ 设置不支持 |
| 解码器不支持低延迟模式 | `CODECAPI_AVLowLatencyMode = TRUE` → `E_INVALIDARG` | ⚠️ 设置不支持 |

**结论：微软的 H.264 解码器 MFT 本身就有约 27 帧的固定输出管线，
且它不接受任何降低管线的设置。** 这不是配置问题，是解码器选型问题。

### 这也解释了为什么 `decode-probe` 没暴露它

`decode-probe` 是**离线解码一个文件**：喂完所有访问单元再排空，
最后统计「共解出 90 帧」看起来完全正常 —— **它把管线里的帧也排出来了**。
只有实时链路（边收边解、看某一时刻的解码进度）才会暴露这 900 ms。

**教训：离线批处理测不出实时管线的延迟。**

## 下一步（按优先级）

1. **换解码器**：改用 D3D11 Video Decoder API（NVDEC / QuickSync 硬件解码）。
   这是实时链路的正确做法，硬件解码器没有这种固定管线，
   而且省 CPU、支持 1080p60。这是当前最高优先级的性能问题。
2. **端到端延迟实测**：发送端在包头写入 `GetTickCount64()`（同机两进程共享），
   接收端解出时相减即可得到**真实的采集→显示延迟**，而不是分段估算。
3. 接入 WinUI 渲染（NV12 → D3D11 交换链 / SwapChainPanel）。
4. 远程控制（SendInput + 帧号绑定防陈旧点击）。
5. 单独应用音频（WASAPI 进程回环，必须子进程隔离）。

## 附：这一轮修掉/发现的坑

| 现象 | 根因 |
|---|---|
| `ICodecAPI` 设置"没生效" | 值必须在 `SetOutputType`/`SetInputType` **之前**下发，放在之后等于没设 |
| 找不到 `ICodecAPI` 定义 | 它声明在 `strmif.h`（DirectShow 头），不在 `codecapi.h` |
| `ComPtr<...>` 报 C7568「缺参数列表」 | `using Microsoft::WRL::ComPtr;` 写在**类内部**会让 MSVC 解析失败，必须放命名空间作用域 |
| `Start-Process` 启动进程后命令挂住 | 该 harness 下不可用，改用后台任务分别启动收发端 |
| 接收端统计少 27 帧 | 解码器内部缓存的帧没有排空，需要 `MFT_MESSAGE_COMMAND_DRAIN` |
